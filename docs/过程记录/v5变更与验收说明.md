# v5 复审修订与验收说明

日期：2026-10-30。配套：实施计划v5.md、schema-v5.sql。

## 本次修订

1. 遗失找回采用scrap_orders.disposal_type=recovery，关联原loss明细，明确审批、自批、库位和质量；找回不恢复原责任关系。
2. 幂等操作身份、唯一键、请求摘要和业务关联长期保留；90天只清理响应内容。同键已处理就不再执行，不受24小时窗口影响。
3. 发放关系统一用closed_at与close_reason结案；loss关联核销明细。未结案唯一索引不再依赖returned_at，找回后可正常再次发放。
4. 固定资产盘盈生成adjustment_gain入库，再建卡；资产来源仍为入库明细，调整明细通过复合外键贯通。
5. 耗材调整记录观察时间、账面量、实盘量及库存version；审批发现快照过期则回滚，重新核实。质量转换采用一出一入、总量不变的调整单。
6. 责任人转移关联同一个transfer_id，写归还和发放两条事件，关闭旧关系、建立新关系；不另写第三条重复状态事件。
7. refresh轮换采用保留旧摘要的会话族记录。10秒内旧令牌只返回已轮换提示；响应丢失且没有共享成功结果时重新登录。logout与refresh共用auth路径cookie，明确撤销与清除方式。
8. 发放、转移、用户停用共用用户行锁；管理员人数变更先锁租户。终结单头冻结执行信息，原发放记录只允许追加一次结案字段。
9. 保留跨租户复合外键；M0评估实现成本但不自动降级。学校B1–B5在M1前确认，新增一期业务重新估算M2/M3工作量。

## SQL交付及边界

schema-v5.sql为独立新库基线，共24张表。保留v4，未生成生产升级迁移。移除用户手机号字段，增加file_jobs、adjustment_orders/items及登录锁定字段，原值与安全库存允许为空。

数据库已表达：租户关联、数量形状、调整快照字段、来源外键、流水来源四选一、一次结案、未结案资产唯一性、审批快照字段一致性、历史追加保护和终结单头/明细更新保护。

仍必须由事务服务保证的跨行规则：

- 同一次loss只允许一次成功recovery；核销/找回时校验卡片当前状态与原核销明细类型。
- 实际发放卡数等于actual_qty；资产必须属于同一物资，采购退货引用采购来源；领用人必须启用。
- 调整头类型与明细形状一致；质量转换的两笔流水数量相等、方向相反；每次库存变化version加1。
- 库存调整的version、book_qty审批时仍有效；期初/入库/调整/资产事件同事务。
- 转移两张业务单和两条事件的transfer_id一致；归还时关闭正确的原发放关系。
- pending单据提交后不能通过普通业务接口追加明细；入库作为即时执行命令，仅在创建事务内插入明细。数据库冻结触发器不单独验证创建事务身份，运行角色授权和服务入口仍不可省略。
- 幂等占位、业务变化、最终响应同事务，禁止单独提交占位；90天清理只更新response，不删除被业务外键引用的行。
- 禁用和降级检查使用约定锁顺序；登录失败锁定不应阻止管理员回收或交接资产。

运行角色与迁移角色授权由部署脚本按实际角色配置。SQL附有授权模板，但未在未知集群中创建全局角色，不声称实际数据库权限已部署。

## 必测场景

| 场景 | 预期 |
|---|---|
| 遗失→找回→再次发放 | 旧关系loss结案，recovery审批成功，建立新未结案关系 |
| 两人同时审批同一次找回 | 仅一次生效，不重复恢复或写事件 |
| 幂等响应90天清理后重放 | 返回已处理与业务关联，不再次建单、转移或扣库存 |
| 同键不同请求内容 | 始终409 |
| 盘盈资产 | 调整明细→入库明细→卡片→事件来源完整 |
| 申请调整后库存先出后入恢复同量 | 因version变化仍判快照过期 |
| 可用转损坏 | available扣减、damaged增加相同数量，总库存不变 |
| 转移与停用同时发生 | 用户锁序列化，停用后不得新增该用户在用资产 |
| 两名管理员同时被降级 | 租户锁保证至少保留一名启用管理员 |
| 修改已完成单的执行人/时间/数量 | 数据库拒绝 |
| refresh成功响应丢失 | 明确重新登录，不无限重试或错误签发重复轮换令牌 |
| 转移失败中途回滚 | 归还、发放、责任人、两条事件全部回滚 |
