# 学校总务处出入库管理系统 v5 审核意见

审核对象：`实施计划v5.md`、`schema-v5.sql`、`v5变更与验收说明.md`（均为 2026-10-30 基线）
审核人：WorkBuddy　审核日期：2026-10-30

> 结论先行：**v5 在工程严谨度上明显优于常见的一次性设计稿**——多租户复合外键 + 服务层过滤双重隔离、append-only 触发器 + 运行角色授权 + 应用约束三层防篡改、幂等键长期保留、统一锁顺序 + 乐观版本号、资产状态机 + 事件溯源 + 对账口径，整体闭环完整。以下意见以"查漏补缺、消除歧义、降低部署风险"为主，按严重级别排序。

---

## 一、一致性 / 文档问题（建议优先修正）

### C1【中】库存调整的 reason_category 列表与 schema 不一致
- `实施计划v5.md` §3 库存调整一行写原因类别为"（盘盈、盘亏、录入错误、其他）"。
- `schema-v5.sql` 中 `adjustment_orders.reason_category` 实际为 `('gain','loss','entry_error','quality_change','other')`，**多了 `quality_change`**。
- 复审补充规则（第 240 行）已用 `adjustment_orders(type=quality_transfer)` + `reason_category='quality_change'` 承载"可用↔损坏"转换，但 §3 主表未同步。
- **建议**：在 §3 库存调整处补全"质量转换（quality_change）"类别，避免评审 schema 时按文档认为缺少该枚举。

### C2【低】附录A 把 v4 已有字段标成"新增"
- 附录A 第 7、19 项将 `allow_self_approval`、`safety_stock`、`unit_price`、`original_value` 标为"新增"，但复审补充第 245 行已自承"以上在 v4 已存在；本次为保留或空值规则调整"。
- **建议**：修正附录A 标注，或加脚注说明"以配套 DDL 为准"，避免交付评审时产生"v4 缺失这些能力"的误读。

### C3【中】`users.auth_version` 列用途与 §2 会话撤销描述不匹配
- schema 有 `users.auth_version INTEGER DEFAULT 1`，但 §2 的会话撤销机制只描述"refresh 会话存摘要与撤销状态、账号禁用/改密/重置密码撤销会话"，未说明 `auth_version` 如何参与校验。
- 当前 `auth_sessions` 没有保存"创建时的 auth_version 快照"，若想靠 auth_version 让旧会话在改密后失效，机制不自洽。
- **建议二选一并在文档写明**：
  1. 改密/禁用时对所有该用户 `auth_sessions` 写 `revoked_at`（当前 schema 已支持，推荐）；或
  2. 在 `auth_sessions` 增加 `auth_version_snapshot` 列，refresh 时与 `users.auth_version` 比对。
  并删除未使用的方案，避免上线后实现与文档脱节。

### C4【低】DDL 基线 vs Alembic 迁移的边界需再澄清
- 计划开头说"schema-v5.sql 是新库基线，不是对既有生产库直接执行的升级脚本"；§10 又说"所有 schema 变更通过 Alembic"。
- **建议**：在 §10 明确——`schema-v5.sql` 仅用于 M0 空库验证与评审；生产迁移由独立的 Alembic 脚本（含数据清洗：跨租户引用、无效数量、重复编码、来源缺口）承载，二者不是同一产物。

## 二、SQL / DDL 技术风险

### S1【中】quality_transfer 的"单行双流水"模型不对称（易误用）
- `adjustment_items` 对质量转换只写 `direction='out'` + `to_quality`，却由事务服务写**一出一入两条 `stock_ledger`**（依赖 `uq_adjustment_ledger_direction` 允许同一 `adjustment_item_id` 的 in/out 各一条）。
- 风险：后续维护者可能只看到一条 `direction='out'` 的明细，误以为只出了库存。
- **建议**：要么拆成两条 `adjustment_items`（一条 out、一条 in，共享 `transfer_id`），要么在 `adjustment_items` 注释和 §4 文档中明确"质量转换明细仅记源方向，目标方向由审批事务补写，受唯一索引约束"。

### S2【中】部分发放/整单零发放缺少数据库层约束
- `outbound_items.actual_qty <= requested_qty` 已有 CHECK，但：
  - 实发少于申请时 `shortfall_reason` 是否必填——无 CHECK；
  - 整单所有 `actual_qty=0` 却标记 `completed`——无约束（仅靠服务层"整单实发0应取消"）。
- **建议**：在 `outbound_items` 增加 `CHECK (actual_qty = requested_qty OR shortfall_reason IS NOT NULL)`；整单零发放由 `outbound_orders` 执行逻辑/M2 测试强覆盖，并在评审清单点名。

### S3【低】幂等唯一键含 `actor_id`，键空间为"每操作者"
- `operation_requests` 唯一约束为 `(tenant_id, actor_id, operation, idempotency_key)`。
- 若同一笔业务由不同操作者（或系统任务）以相同幂等键重放（如批量导入重试），不会被 409 拦截。
- **建议**：确认幂等键由客户端会话保证全局唯一即可；若需跨操作者防重，去掉 `actor_id` 或改为 `(tenant_id, operation, idempotency_key)`。当前设计大概率可接受，但应在 §5 写明语义。

### S4【低】`auth_sessions` 无限增长
- 过期/已撤销会话只增不删，长期运行表膨胀，且 refresh 查询需扫 family。
- **建议**：增加定期清理（如保留最近 N 天 + 已撤销即清），并写入 §8 备份/清理策略。

### S5【低】多数表无 `updated_at`
- 除 `inventory` 外均无最后修改时间。当前由事件/流水/审计表覆盖，影响小；但基础资料（部门、库位、物资）未来若有"最后修改人/时间"诉求需补列。

### S6【中，需明确】PostgreSQL 版本门槛
- `stock_ledger` 使用了 `num_nonnulls()`，该函数自 **PostgreSQL 14** 起提供。
- **建议**：在 §2 技术方案显式声明"生产 PG 主版本 ≥ 14"，并在 M0 用同版本建库验证，避免低版本 DDL 直接失败。

### S7【中】`protect_order_header` 白名单冻结了审批类单据的 reason
- 白名单为 `(status, operator_id, operation_id, executed_at, self_issued, approver_id, approved_at, self_approved, allow_self_approval_snapshot)`，不含 `reason`/`responsibility_opinion`/`evidence_file_keys`。
- 后果：pending 阶段也无法修改理由（与"取消后重新申请"一致，但 UI 需让申请人能看到原 reason 再决定重申请）。
- **建议**：在 §7 页面设计明确"驳回/取消后重新申请时携带原内容副本"，避免用户体验断层。

## 三、业务逻辑缺口

### B1【中】期初切换（cutover）缺操作级步骤
- §8 只说"库存首次上线时冻结旧账，明确切换时点；禁止旧账和新系统同时扣减同批业务"。
- **建议**：补一份切换检查清单（停旧系统写入 → 导出期初快照 → 系统内部对账为0 → 启用新系统 → 旧账只读封存），并作为 M4 前置。

### B2【中】个人/部门领用后"耗用"无记录
- §1 明确一期不建部门易耗品持有账、不扣后续耗用。若学校有"个人领用后消耗统计"诉求，一期无法满足。
- **建议**：在附录B 增加确认项（如 B9），明确告知学校此限制，避免试点后才发现缺口。

### B3【中】遗失责任认定附件的结构与保留期未落到表
- `scrap_orders.evidence_file_keys` 为 JSONB，文档说"受控对象键、按审批证据保留期管理、不随导出 TTL 删除"，但**保留期没有对应字段**，仅停留在文字。
- **建议**：在 `scrap_orders` 或独立证据表增加 `evidence_retention_until`，或在 §8 明确证据文件的保留策略与清理作业，避免与导出文件混管导致误删。

### B4【中】固定资产"actual_qty == 发卡数"未数据库层保证
- `outbound_items`（fixed）的 `actual_qty` 必须等于其下 `outbound_assets` 行数。目前仅靠服务层 + M3 测试（"申请5台实发3台记录3张卡"）。
- **建议**：在 M3 验收明示该不变量，并考虑应用层在提交时断言 `COUNT(outbound_assets) = actual_qty`。

### B5【低】低库存提示无通知（已声明一期不做）
- 可接受，但建议在仪表盘之外，预留二期通知的钩子字段（如 `items.safety_stock` 已具备）。

## 四、安全与运维

### SEC1【高】防篡改依赖"运行角色无表所有权/无 TRIGGER 权限"，但角色未随 DDL 创建
- `schema-v5.sql` 末尾只有授权**模板注释**，未创建 `inventory_runtime` 角色。注释本身也承认"不等于防篡改认证，须由 DBA 实际执行 GRANT"。
- 这是部署验收的**硬门槛**：一旦 DBA 漏配，append-only 触发器可被 superuser/owner 绕过（虽非应用账户，但运维账户若过宽仍有风险）。
- **建议**：把"实际 GRANT 验证（运行角色仅 SELECT/INSERT 历史表、无 TRIGGER、非 owner）"列为 M1 的**阻断项**，并在交付包中附带可执行的授权脚本与校验断言。

### SEC2【中】`audit_logs.ip` 属个人敏感信息，保留期未定
- §2 个人信息最小化聚焦手机号，但 `audit_logs.ip INET` 同样属敏感信息，保留期依赖 B6 学校确认。
- **建议**：在隐私章节明确 IP 的最小化采集（是否需全量）、是否匿名化、最长保留上限，避免无限留存引发合规风险。

### SEC3【中】PITR 恢复演练的"对账脚本"尚未作为交付物给出
- §8/§9 要求恢复演练附验收脚本（恢复后跑对账并记录耗时），但未随 v5 提供脚本本身。
- **建议**：把对账脚本（§9 内部一致性 5 条 + 实物抽盘）列为 M4 前必须交付的代码产物，纳入仓库。

### SEC4【低】登录失败锁定不应阻断管理员回收/交接资产
- 已明确"登录失败锁定不改变 active、不触发资产交接"——方向正确。
- **建议**：在 M1 测试增加"用户 locked_until 期间，管理员仍可执行其名下资产回收/转移/停用前检查"，确认服务层绕过登录锁定。

## 五、正向评价（值得保留的设计）

1. **多租户隔离双保险**：复合外键（tenant_id + id）+ 服务层强制过滤，且文档明确要求原生 SQL、后台任务、批量导入、对象存储下载全覆盖测试。
2. **不可篡改三层兜底**：append-only 触发器 + 运行角色授权 + 应用约束；并在注释中诚实标注"superuser/owner 仍可改 schema，不等于防篡改认证"，工程诚信好。
3. **幂等设计严谨**：唯一键 + 请求摘要 + 业务关联长期保留，90 天仅清响应内容，重放返回 `ALREADY_PROCESSED` 而非重新建单。
4. **并发模型成熟**：统一锁顺序、INSERT…ON CONFLICT DO NOTHING 后再 SELECT FOR UPDATE（避免锁不存在行）、库存 version 乐观检查防快照过期、仅重试 40P01/锁超时且复用原幂等键。
5. **资产全生命周期闭环**：状态机（§3.1）+ `asset_events` 事件溯源 + `stock_ledger` 流水 + 每日对账口径（库存结余=流水累计、资产状态=末事件、每张 in_use 资产恰一条未了结发放），自洽性强。
6. **权限治理到位**：自批开关留痕（前后值+操作者+快照）、最后一个管理员保护、发放 self_issued 标记可查。

## 六、建议的处理优先级

| 优先级 | 编号 | 动作 |
|---|---|---|
| P0（阻断/高） | SEC1 | 提供并验证运行角色授权脚本，列入 M1 阻断项 |
| P0 | S6 | 显式声明 PG ≥ 14，M0 同版本验证 |
| P1（中） | C1、C3 | 修正 §3 枚举、明确 auth_version 撤销机制 |
| P1 | S1、S2 | 明确 quality_transfer 模型；补部分发放/零发放约束 |
| P1 | B1、B3 | 补期初切换清单；证据保留期落字段 |
| P1 | SEC2、SEC3 | 明确 audit IP 保留；交付对账脚本 |
| P2（低） | C2、C4、S3、S4、S5、S7、B2、B4、B5、SEC4 | 文档澄清、次要约束与测试覆盖 |

> 说明：v5 是自认的"设计交付"，不等于运行系统或验收通过；以上意见应在 M0（DDL 评审通过）前闭环高/中优先级项，低优先级可随 M1–M3 实现同步消化。本审核未实际运行 PostgreSQL（本机无 psql/Docker），SQL 正确性以静态阅读 + 文档一致性核对为准，最终以 M0 空库执行 + 负向约束测试为准。
