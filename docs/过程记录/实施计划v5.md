# 学校总务处出入库管理系统 — 实施计划 v5

版本日期：2026-10-30。配套：`schema-v5.sql`（新库基线，已同步本次修订）、`v5变更与验收说明.md`。

本项目独立于校园报修小程序；后续可通过资产编号关联维修记录。一期按单校运营、多租户数据结构建设。本文取代 v4 中冲突的业务规则；DDL 为新数据库基线，不是对既有生产库直接执行的升级脚本。v4→v5 的逐项变更见附录A，需学校确认的事项见附录B。

## 1. 目标与范围

一期完成 Web 管理后台、领用人 Web 轻端、易耗品仓库库存、固定资产一物一卡、采购入库、领用申请与发放、归还、责任人转移、采购退货、报废与遗失核销审批、库存调整（盘盈盘亏）审批、Excel 期初导入、台账导出及试点。

二期独立开展微信小程序、扫码盘点、通知；三期讨论折旧。二期表本期不创建，避免未定规则成为既定数据库接口。一期的库存调整单只解决"账实不符后如何合规纠正"，不包含盘点计划、扫码、盘点任务分配等流程，这些仍属二期。

一期不建立部门易耗品持有量账，不对领用后的耗用再次扣仓库库存。领用人不能申请"部门易耗品库存报损"；仓库易耗品报损、库存调整均由管理员发起。

业务术语约定：**领用 = 申请 + 管理员发放确认，不是审批**；审批用于报废、遗失核销、遗失找回、仓库耗材报损、库存调整五类单据（下称"审批类单据"）。

## 2. 技术方案

后端 Python/FastAPI、SQLAlchemy 2.x、Alembic；数据库 PostgreSQL；前端 Vue 3/Vite/Element Plus/Pinia/Router。应用以容器部署，对象存储保存私有导入导出文件。开发测试使用与生产同一 PostgreSQL 主版本。

**认证与会话**
- JWT access + refresh，密码使用 bcrypt。refresh 会话在服务端存摘要与撤销状态，采用轮换；账号禁用、改密、重置密码撤销会话，接口检查用户与租户状态。不能只相信 JWT 中长期不变的角色信息。
- 令牌存放：refresh 令牌放 httpOnly + Secure + SameSite=Strict cookie，Path=/api/v1/auth（覆盖 refresh 与 logout）；access 令牌只保存在前端内存，不写 localStorage。refresh 与 logout 接口除 SameSite 外再要求自定义请求头校验（CSRF 防护）。前端启用 CSP，禁止内联脚本，用户输入一律转义输出。
- 并发刷新：每次轮换保留旧令牌摘要与 revoked_at（消费时间），并在同一事务内生成同会话族的新会话记录。旧令牌10秒内重现返回 REFRESH_ALREADY_ROTATED，不签发新令牌；前端单飞刷新并跨标签页共享成功结果。若原成功响应丢失且没有其他标签页提供新结果，明确要求重新登录，不循环重试。超出窗口重现撤销该会话族并写审计。logout 使用 cookie 或有效 access 中的 session_id 定位并撤销会话族，按同一 Path 清除 cookie；刷新检查 Origin 白名单及自定义头，禁止任意来源凭据 CORS。
- 登录防护：同一用户连续失败5次锁定15分钟（次数与时长为租户级可配置，下限不可关闭）；失败提示不区分"用户不存在/密码错误"；IP 级限流在反向代理或网关层实施。密码至少10位，不得与用户名相同；新建账号、管理员重置密码后首次登录强制改密（users.must_change_password）。锁定、解锁、强制改密均写审计。

**个人信息最小化**：一期不采集手机号，users 表不含手机号及相关加密、盲索引字段，姓名明文仅对授权角色展示。如二期小程序绑定或学校要求保留联系方式，届时再引入手机号字段，并沿用以下原则：Fernet 加密，盲索引使用独立密钥 HMAC-SHA256 对标准化手机号及 tenant_id 计算，不使用普通哈希，密钥版本分别记录，轮换需双版本查询过渡及重新索引方案。日志任何时候不记录令牌、密钥及个人敏感信息明文。

**数据库账号与不可篡改**：运行账号与迁移账号分离。运行账号对 audit_logs、stock_ledger、asset_events 仅授予 INSERT/SELECT。单据头进入 completed/approved/rejected/cancelled 后禁止 UPDATE/DELETE，执行人、执行时间和业务字段一并冻结；入库单提交即执行，头与明细不可修改。明细执行后禁止 UPDATE/DELETE；原发放关系仅允许追加一次结案信息，不允许更换资产、物资或来源。新增备注写审计记录，不改历史单据。应用层约束与数据库层约束并存，互为兜底。

## 3. 明确的业务决策

| 项 | v5 规则 |
|---|---|
| 部分发放 | 一张申请只执行一次；实发少于申请时填写差额关闭原因，剩余量关闭。需要更多物资重新申请；本期不补发。页面提供"按差额再次申请"（复制原申请的未满足量，仍须重新提交）；领用目录显示"有货/不足"以减少部分发放。 |
| 固定资产申请 | 按物资型号和数量申请；执行时在独立资产清单中选择具体资产卡，每卡计1件。 |
| 库存质量 | 易耗品库存以学校、物资、库位、质量状态区分；质量为 available/damaged。损坏品不参与可领用数量。 |
| 耗材归还 | 必须关联原发放明细，累计归还不得超过该明细实发量；仅管理员验收接收入库。无法找到历史来源的存量以期初导入处理。 |
| 资产归还 | 引用原资产发放记录；原记录尚未归还且资产责任人与领用关系匹配。可用归还转 in_stock，损坏归还转 repair，均清空责任人。 |
| 资产责任人转移 | 在职调动、人员交接时由管理员发起。系统以同一个 transfer_id 在同一事务内生成归还验收和 transfer 发放，写 return（in_use→in_stock）及 issue（in_stock→in_use）两条事件，事件按 id 排序。关闭旧发放关系 close_reason=transfer，建立新关系；对事务外最终仍为 in_use，不再重复写第三条 transfer 状态事件。不新增表；转移不经审批，但转出人、受让人、原因必填并写审计。 |
| 采购退货 | 耗材关联采购入库明细，累计供应商退货不超过原采购量，同时扣当前可用仓库库存；固定资产允许已建卡的在库资产逐件退货，转 returned_to_supplier。采购退货仅管理员发起与执行，不属于审批类单据。 |
| 耗材来源口径 | 一期无批次库存，供应商退货来源是额度和业务追溯依据，不承诺物理批次追踪、FIFO、成本分摊，也不管理有效期（需学校书面确认，见附录B）。 |
| 在用资产报废 | 领用人可基于本人尚未归还的发放记录申请；审批执行前必须归还验收，资产处于 in_stock/repair 且无人负责。归还后仍通过原发放记录认定申请依据。 |
| 资产遗失核销 | 资产确实无法归还（遗失、被盗）时，领用人可基于本人未归还的发放记录申请，管理员也可发起，必须填写经过说明和责任认定意见。属审批类单据。执行时资产转 lost，清空责任人，原发放记录标记为"因遗失核销了结"并关联核销明细（closed_at、close_reason=loss、loss_scrap_item_id）；在库或维修中遗失没有未结案发放关系时不虚造发放记录。 |
| 遗失资产找回 | 管理员创建 scrap_orders(disposal_type=recovery)，明细关联原 loss 明细及找回库位/质量，适用同一自批规则。审批后 lost→in_stock/repair，原责任关系保持结案；同一次遗失只允许一次审批成功的找回，再次遗失应创建新的核销记录。 |
| 仓库耗材报损 | 仅管理员申请，指定库位、质量、数量；审批时扣对应库存。领用后耗用不再扣库。 |
| 库存调整（新增） | 仅管理员申请，属审批类单据。耗材：指定库位、质量、数量、方向（盘盈/盘亏）、原因类别（盘盈、盘亏、录入错误、其他）和必填说明；审批时增减对应库存并写 stock_ledger（类型 adjustment）。固定资产盘盈（实物存在但无卡）：在调整单内补充建卡信息，审批后生成 inbound_orders(type=adjustment_gain) 及逐明细关联的入库明细，再建卡并写资产事件（found_gain）；卡片来源仍统一指向入库明细；固定资产盘亏一律走遗失核销，不走调整单。 |
| 审批执行 | 审批通过与处置一个事务；不足或状态不合法时事务回滚，申请保持 pending，不自动变成 rejected，页面向申请人和审批人展示失败原因。适用于报废、遗失核销、遗失找回、报损、库存调整。 |
| 自批 | 默认禁止，范围仅限审批类单据。学校管理员可显式修改开关（存于 tenants.allow_self_approval），必须记录原因、修改前后值及操作者（写 audit_logs）；审批时记录当时开关快照及 self_approved。自批审计突出显示。领用发放时发放人与申请人为同一人，记录 self_issued 标记，不禁止但可查询。 |
| 管理员配置 | 学校上线时至少设置2个启用的管理员账号；如学校只有1名总务人员，须书面确认启用自批开关（附录B）。系统禁止停用或降级最后一个启用的管理员。 |
| 用户停用 | 停用用户前检查其名下 in_use 资产和 pending 单据：存在 in_use 资产须先归还或转移；pending 单据须先取消或由管理员处理。检查不通过则拒绝停用并列出清单。 |
| 金额口径 | 采购入库明细记录单价（可空，期初导入可补），资产卡记录原值（可空）。仅用于记录和统计，不做库存计价、不核算加权成本、不做折旧。是否必填由学校确认。 |
| 管理方式 | 物资创建时确定类型（耗材/固定资产），已发生任何业务后不得改类型。固定资产与低值易耗品的划分口径由学校确认；固定资产编号规则按租户配置前缀加顺序号，生成后不可修改、不复用。 |
| 低库存提示 | 物资增加安全库存字段（可空）；仪表盘展示可用库存低于安全库存的清单，一期不做通知推送。 |

### 3.1 资产状态转换矩阵

状态：in_stock、in_use、repair、scrapped、returned_to_supplier、lost。每次转换写资产事件，禁止通过通用接口直接改状态或责任人。

| 起始状态 | 目标状态 | 触发业务 | 审批 |
|---|---|---|---|
| （无） | in_stock | 采购入库建卡 / 期初导入 / 盘盈入库（调整单） | 调整单需审批 |
| in_stock | in_use | 领用发放 | 否 |
| in_use | in_stock | 归还验收（可用） | 否 |
| in_use | repair | 归还验收（损坏） | 否 |
| in_use | in_use | 责任人转移（同事务归还加重新发放） | 否 |
| in_stock ↔ repair | repair ↔ in_stock | 管理员维修事件（双向） | 否 |
| in_stock、repair | scrapped | 报废（执行前必须已归还，无责任人） | 是 |
| in_stock、repair、in_use | lost | 遗失核销 | 是 |
| lost | in_stock、repair | 遗失找回 | 是 |
| in_stock | returned_to_supplier | 采购退货 | 否 |

终态：scrapped、returned_to_supplier，不能恢复。lost 不是终态，仅可通过审批的找回转出。在用资产送修一期先归还。

## 4. 数据结构与数据库保证

配套 DDL 共24张表：tenants、departments、users、auth_sessions、locations、categories、items、suppliers、operation_requests、file_jobs、inbound_orders、inbound_items、asset_cards、outbound_orders、outbound_items、outbound_assets、inventory、stock_ledger、asset_events、scrap_orders、scrap_items、adjustment_orders、adjustment_items、audit_logs。

相对 v4：import_jobs 扩展并更名为 file_jobs（job_type 区分导入/导出，保存模板版本、映射版本、文件摘要、对象存储键、过期时间，所有查询按租户过滤）；新增 adjustment_orders、adjustment_items；scrap_orders 增加 disposal_type（scrap/loss/recovery/stock_damage）以承载报废、遗失核销、仓库耗材报损三类共用的审批执行流程；tenants 保留 allow_self_approval；users 增加 must_change_password、failed_login_count、locked_until，不含手机号字段；items 保留 safety_stock 并允许为空；inbound_items 保留 unit_price；asset_cards.original_value 改为可空；asset_events、outbound_assets 增加遗失核销、转移所需的关联与标记。

**单据类型与表的对应关系**（依据 v4 表结构推定，评审 schema-v5.sql 时逐项核对）：

| 业务单据 | 头表（类型） | 明细表 | 备注 |
|---|---|---|---|
| 采购入库 | inbound_orders（purchase） | inbound_items | 耗材增库存，固定资产逐件建卡 |
| 归还验收 | inbound_orders（return） | inbound_items，关联原发放明细 | 耗材入库存；资产更新状态 |
| 期初 | inbound_orders（opening） | inbound_items | 来自 file_jobs 确认 |
| 领用 | outbound_orders（requisition） | outbound_items，资产另有 outbound_assets | pending→已执行/取消 |
| 责任人转移 | outbound_orders（transfer）加 inbound_orders（return） | 同上 | 同事务生成 |
| 采购退货 | outbound_orders（purchase_return） | outbound_items，关联原采购入库明细 | 仅管理员 |
| 报废 / 遗失核销 / 仓库报损 | scrap_orders（disposal_type） | scrap_items | 审批类 |
| 库存调整 | adjustment_orders | adjustment_items | 审批类 |

关键关系使用 tenant_id + id 复合外键，禁止跨校关联。物资类型通过复合外键约束：库存只引用耗材、资产卡只引用固定资产。物资编码、用户名和单号租户内唯一；学校代码与随机二维码 token 全局唯一是明确例外，主键也是全局唯一。

QR token 由服务端密码学随机生成至少128位熵，不作为免登录凭证。扫码仍检查租户与角色。库存流水记录库位、质量、方向、数量、结余及具体单据明细（含 adjustment 类型）；固定资产使用 asset_events，不往易耗品结余字段填伪造值。

已执行单据、明细、流水和资产事件禁止普通编辑、删除（数据库层约束见第2节）；纠错通过关联来源的反向业务单据（库存调整、遗失找回、采购退货等）。用户、物资、仓库采用停用，不复用业务编码。DDL 中 CHECK/外键保证行级形状；累计额度、行数等跨行规则由事务服务保证，见第5节。

**多租户成本验证门槛**：M0 阶段先用 items、inventory、asset_cards、outbound_items 四张核心表原型化复合外键，评估 SQLAlchemy 模型编写、Alembic 迁移和测试编写的实际成本，评审记录是否全量推行。M0用于优化建模方式和估算成本，不取消关键业务复合外键。读取权限仍由服务层保证，不能用约束替代查询过滤。

## 5. 事务、幂等与并发

所有写命令带 Idempotency-Key。operation_requests 对 tenant_id、actor_id、operation、key 建唯一约束，并保存规范化请求摘要、目标与成功响应；同键不同请求返回409，同键同请求返回原结果。幂等操作标识、唯一键、请求摘要及业务关联长期保留，不按90天删除。完整成功响应保存90天后可清空，同键同摘要此后返回 ALREADY_PROCESSED 与业务关联；同键不同摘要始终409。新业务必须使用新键，不把窗口外重放当作新请求。

操作记录插入与业务写入在同一事务提交；失败整体回滚，重试可重新执行。并发同键冲突的后到请求等待先到提交后读取结果。不同键执行同一单据仍须锁单据并校验 pending，不能再次执行。

**事务隔离**：默认 READ COMMITTED，依靠显式行锁和唯一约束保证正确性；一期不使用 SERIALIZABLE。设置 lock_timeout 与 statement_timeout；仅对死锁（40P01）和锁超时有限次数重试，始终复用原幂等键。

锁顺序统一为：操作键→租户行（账号变更、自批设置与审批时）→按ID排序的用户行（账号变更、发放、转移时）→目标单据→按类型和ID排序的来源明细→按ID排序的资产卡→按完整主键排序的库存行。所有入口（含库存调整、遗失核销、转移）遵守顺序。

库存行不存在时先 INSERT ... ON CONFLICT DO NOTHING 建立零库存行，再 SELECT FOR UPDATE；禁止仅锁查询不存在的行。出库条件更新须 quantity >= 扣减量，并检查影响行数（库存调整的盘亏、报损同理）。入库、出库、归还、报废、调整、流水和状态同事务提交。

累计归还/采购退货必须锁定来源明细后统计已执行记录；固定资产归还、转移、遗失核销锁原发放记录与卡片。发放数量与资产清单条数一致；卡片 item_id、学校与明细匹配，且状态可发放。申请正数量，实发0到申请量；整单实发0时应取消而不是完成。

所有可审批/发放内容在提交后冻结；本期修改方式为取消后重新申请。审批不能只信前端传入的申请人、金额或 self_approved 字段。

## 6. 权限与租户边界

学校角色仅 admin/user。user 只看可领用目录与有货/不足、本人申请与资产；可以申请领用、取消本人 pending 申请、申请本人资产报废、申请本人资产遗失核销。管理员执行库存操作、验收归还、转移、审批、库存调整及人员管理。

一期取消租户列表/创建公共接口。租户创建、到期日、平台状态通过受控运维命令处理并留审计；学校管理员只能维护本校显示信息与自批开关，不得延长期限或枚举其他学校。

登录提交学校代码+用户名+密码，用户名租户内唯一。所有列表、详情、文件链接、导入任务、二维码和导出任务均从服务端身份确定租户。复合外键不代替读取权限过滤。租户隔离测试必须覆盖原生SQL、后台任务、批量导入及对象存储下载。

## 7. 一期接口与页面

认证：login/me/refresh/logout/change-password。基础资料：部门、库位、供应商、分类、物资、用户管理（停用时执行第3节检查）。学校设置只提供本校读取/有限字段修改。

入库：创建并执行采购/归还/期初单（管理员）；出库：领用申请、采购退货申请（后者仅管理员）、执行、取消；责任人转移（管理员）；报废/遗失核销/仓库报损：申请、审批执行、驳回、取消；库存调整：申请、审批执行、驳回、取消；遗失找回：申请、审批执行、驳回。状态转换使用独立命令接口，不开放任意 status PATCH。

资产：查询、二维码、管理员维修事件；禁止通过通用 CRUD 改责任人或状态。库存提供管理员明细与领用人目录两种明确响应模型；流水及完整资产事件仅管理员。导入提供预览、错误清单、确认和任务状态；导出按角色范围授权，导出任务记录在 file_jobs。

管理员页面：仪表盘（含低库存提示）、基础资料、入库、领用发放、转移、采购退货、归还验收、库存与流水、资产、报废与遗失核销审批、库存调整、导入导出、审计、本校设置。领用人页面：登录、可领用目录、申请（含按差额再次申请）、本人申请、本人资产、本人资产报废/遗失申请、个人中心。

## 8. 导入与数据保护

三类模板：物资主数据、固定资产期初、耗材期初库存。预览只写临时任务；确认时核对文件摘要、映射版本、租户和幂等键，重新校验并在一个事务内生成业务数据。重复业务编码默认拒绝，不直接覆盖已发生业务的记录。单价、原值为可选列。

期初资产生成 opening 入库明细、卡片及资产事件；期初耗材生成 opening 入库及库存流水。库存首次上线时冻结旧账，明确切换时点；禁止旧账和新系统同时扣减同批业务。

**备份与恢复**：优先采用云厂商托管 PostgreSQL 的时间点恢复（PITR）；如自建，则每日备份加 WAL 归档。备份异地/独立权限保存，保留30天；目标 RPO≤15分钟，RTO≤4小时，在试点前实际恢复演练。恢复演练须附验收脚本：恢复到指定时间点后，运行对账脚本（见第9节）并记录耗时与结果。应用密钥（JWT 签名密钥等）纳入恢复演练，不与公开导出文件共存。

导出与二维码临时文件7天清理，原始导入文件30天；operation_requests 的完整响应保留90天，操作身份/摘要/业务关联长期保留；审计留存期限由学校在试点前确认。

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| M0 | 技术与DDL验证 | 同版本PG建库成功；Alembic upgrade及无损迁移回退演练；容器、密钥注入可用；多租户复合外键成本验证完成并有评审结论；DDL v5 评审通过 |
| M1 | 身份、权限、租户、幂等、审计 | 跨租户读写/关联/文件访问全拒绝；禁用与会话撤销有效；同键异请求409；登录锁定、强制改密、并发刷新、令牌复用检测测试通过；最后一个管理员保护有效；审计表数据库层拒绝 UPDATE/DELETE |
| M2 | 耗材、导入、入出库、库存调整 | 20并发争抢库存不超发；重复执行只生效一次；库存为0时并发入库不丢增量；5000行预览及确认分别≤60秒；库存调整盘盈盘亏审批后流水与库存一致，审批失败回滚保持 pending |
| M3 | 资产、归还、转移、采购退货、报废、遗失核销 | 申请5台实发3台记录3张卡；同卡争抢仅一方成功；累计超额归还/退货被拒；在用报废先归还后执行；转移同事务完成且责任人正确；遗失核销后原发放记录了结且无法再归还；找回经审批转出 lost；用户停用检查生效 |
| M4 | 一期试点准备及试点 | 先恢复演练达标、权限规则验证，管理员完成培训并独立走通一次完整闭环（入库→领用→归还→报废/调整）；再真实数据试点至少连续10个工作日，系统内部对账差异0，阻断缺陷0 |
| M5 | 一期正式运行 | 备份监控、操作说明、导出交接、回退方案、主体和部署相关手续确认 |
| 二期 | 小程序、扫码盘点、通知 | 独立PRD、schema迁移与验收，不作为一期上线前置 |

**试点对账口径**：
1. 系统内部一致性（由对账脚本每日运行，须0差异）：库存各行结余等于流水累计；资产当前状态等于最后一条资产事件；每张 in_use 资产有且仅有一条未了结发放记录；已了结（归还、转移、遗失核销）发放记录累计不超过实发量；处于 lost、scrapped、returned_to_supplier、in_stock、repair 状态的资产无责任人。
2. 实物抽盘：试点期间每周至少抽盘一次（覆盖全部固定资产高价值类别及随机抽取的耗材品种），差异必须通过库存调整单或遗失核销单处理并留存原因，不得绕开系统改数据。试点结束时不得存在无法解释的差异。

**验收测试规范**：并发与性能测试使用自动化脚本（建议 pytest 加 locust 或等价工具），脚本纳入代码仓库可复现；记录数据规模（物资数、库存行数、资产卡数）、索引、环境和耗时。性能测试基线：2 vCPU/4GB应用、2 vCPU/4GB PG、同区域网络、单次5000行且文件≤10MB；不将目标视为未经测试的承诺。排期在M0后按资源估算并留20–30%缓冲，本文不虚设交付日期。

## 10. 迁移、回滚与实施边界

所有schema变更通过Alembic；schema-v5.sql用来验证新库结构与评审。已有数据升级另写迁移与校验脚本，先清理跨租户引用、无效数量、重复编码和来源缺口。

应用回滚需兼容当前数据库；删除字段等破坏性变更不承诺自动 downgrade 无损恢复，应采用扩展→迁移→收缩及备份恢复方案。已提交业务不能以删库/撤回迁移替代冲正。

开工前即可确定的口径已在v5中落实：一期一次发放关闭差额、部门耗材不建持有账、资产归还后报废、遗失核销与库存调整进入一期、一期不采集手机号。上线前需要学校补充真实台账、部署账号、主体手续、隐私联系人及审计保留期限，并确认附录B各项；B1/B2/B3/B4/B5须在M1前确认，避免返工。M0后重估新增调整、遗失、找回、转移所需的M2/M3工期。v5是设计交付，不等同于运行系统或验收通过。

## 本次复审补充规则（v5定稿口径）

- 库存调整采用快照模式：记录observed_at、账面量book_qty、实盘量counted_qty、方向与差额、库存行version；审批锁定库存行后要求version与book_qty均未变化，否则返回STALE_OBSERVATION、保持pending，申请人取消后重新观察并申请。库存每次变动version加1，数量回到原值也不能绕过过期检查。无行时先建立零库存行再获取快照。固定资产盘盈逐件一行，禁止无差额耗材调整。
- 仓库耗材由可用转损坏或修复时，使用adjustment_orders(type=quality_transfer)，一行指明from_quality/to_quality及正数量，审批同事务写一出一入两条流水，总量不变。锁定两条库存行并校验快照，禁止直接改库存质量。直接报损处置仍走stock_damage，二者不能重复扣减。
- 用户停用/降级、发放、转移使用同一用户行锁，锁后重新检查active与责任关系；管理员数量变更先锁本校tenant行后检查剩余启用管理员。登录失败锁定不改变active，不触发资产交接。管理员可取消已停用流程中存在的pending单。
- 资产发放关系统一以closed_at判定未结案，close_reason为return/transfer/loss/purchase_return；采购退货资产记录创建时即结案，不占用领用关系。lost找回不复活旧发放关系。资产盘盈、找回、报废等事件需携带具体来源明细。
- 审批类含recovery，学校确认的责任认定附件通过disposal单的evidence_file_keys保存受控对象键，访问按租户授权；文件不能随普通导出TTL删除，按审批证据保留期管理。
- 对账增加：每张lost卡对应最新未恢复的loss；recovery只恢复同一卡同一次loss；quality_transfer两笔流水数量相等方向相反；转移两条事件与归还/发放单具有同一transfer_id。
- 附录A中的“新增”以本次配套DDL为准：allow_self_approval、safety_stock、unit_price、original_value在v4已存在；本次为保留或空值规则调整。supplier_return统一使用purchase_return。审计、流水仅追加不代表超级用户无法改动数据库。
