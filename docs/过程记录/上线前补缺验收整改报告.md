## 二、对补交方案的必要修正

1. **工作目录不能代替入口位置。** 中枢文件注释建议“保留嵌套文件，只加 defaults.run.working-directory”不能解决发现问题；工作流必须放在真实仓库根的 `.github/workflows/`，working-directory只影响命令执行目录。[GitHub官方说明](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
2. **测试环境不能直接套用 DEBUG=false。** 本次实际复现：DEBUG=false时，HTTP `GET /health/live/` 返回301并跳转HTTPS，现有测试的200等断言会受影响。规范入口保留CI专用DEBUG=true，生产配置默认false不变；没有放宽生产安全设置。
3. **无需额外启动使用postgres身份的全局worker/beat。** verify_p6/p7自身建立临时库、普通LOGIN、独立Redis与worker/beat，并清理资源。补交文件的DB_USER=postgres后台进程不符合运行身份要求，也没有替代这些隔离夹具；规范入口只准备Redis binary，由原脚本启动其所需进程。
4. **保留原触发范围和哈希门禁。** 补交文件把push限定main/master，并通过去掉hash后只比版本判断requirements；规范入口继续使用 `on: [push, pull_request]` 和完整冻结导出字节比较。
5. **采纳显式G0/M1检查。** 根入口增列verify_schema/verify_runtime步骤，均使用专用campus_inventory基线库；`postgres`维护库仍只用于独立脚本的临时资源管理。

## 五、复验方法与尚未闭环的外部事项

在应用目录执行：

```sh
python scripts/verify_ci_delivery.py --repo-root /Users/andy/Desktop/saas
```

会输出实际根入口及SHA，避免在错误目录内搜索。根入口完全缺失时GitHub无法自行触发，因此该命令也应在提交前执行，不能依赖CI自行发现“CI文件没有提交”。

本地仍无Git checkout或GitHub Actions runner；**真实push/PR自动触发与远端全绿未验证**。需要将根入口、应用、template和自检脚本一并提交到实际仓库，再留存Actions记录。若实际Git根为inventory-v4或django，按CI交付定位说明放置同一template并重新自检。Docker部署实测及B8真实云S3/托管Redis联调继续按原边界在目标环境验收。
