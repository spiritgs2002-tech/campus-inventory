## 4. 二、逻辑走查（按 §6 / §7 / §9）

### 4.1 统一锁顺序（§6）—— 实测与规范一致
规范锁序：`操作键 → 租户行 → 按 ID 排序用户行 → 目标单据 → 按类型/ID 排序来源明细 → 按 ID 排序资产卡 → 按完整键排序库存行`。

| 顺序 | 实现位置 | 落地 |
|---|---|---|
| 操作键（幂等 INSERT） | `idempotency/service.py._execute`：`OperationRequest.get_or_create`（FK KEY SHARE，先持锁） | ✅ |
| 租户行 | `core/services.py.lock_order_context`：`Tenant.objects.select_for_update(no_key=True)` | ✅ |
| 按 ID 排序用户行 | 同上：`User…filter(…).order_by("id").select_for_update(no_key=True)` | ✅ |
| 目标单据 | `orders.decide`→`header_get(…, locked=True)`：`select_for_update(no_key=True)`；`create` 为新建行（唯一约束串行化） | ✅ |
| 按表名排序来源明细 | `posting.lock_sources`：`sorted(mapping.items(), key=db_table)` 逐表 `select_for_update(no_key=True)`；`InboundItem` 因运行账号无 UPDATE 改用 `pg_advisory_xact_lock(hashtextextended("source:…:inbound_items:pk"))` | ✅ |
| 按 ID 排序资产卡 | `posting.lock_sources`：`AssetCard…order_by("id").select_for_update(no_key=True)` | ✅ |
| 按完整键排序库存行 | `posting.lock_stock`：`sorted(set(keys))` → `Inventory…select_for_update(no_key=True)` | ✅ |

死锁防护：`core/services.py` 注释明确 "NO KEY UPDATE serializes mutations without a lock-upgrade deadlock"；`_execute` 对 `40P01`/`55P03` 重试（≤3 次指数退避）。`test_transfer_retry_discards_rolled_back_source_ids` 以 `DeadlockDetected` 模拟首试失败，重放下无残留（StockLedger=4、transfer 入库单=1、库存回滚到 40）——**证明锁序 + 幂等重放组合正确**。

### 4.2 核心工作流（§7）
- **入库**：头+明细同事务、`created_xid` 守卫（`test_inbound_is_immediate_same_xid_and_atomic_on_bad_line` 验 xid 为数字）；admin 即时过账（无 pending 态，符合 admin-only 语义）；坏行（跨租户库位）整单原子回滚、无孤儿记录。✅
- **出库**：`issue`/`requisition`；`actual_qty`/`shortfall_reason`（实发<申请必须填差额原因，否则 `SHORTFALL_REASON_REQUIRED`）；`location`/`recipient` 提交冻结后不可改（`SUBMITTED_LINE_FROZEN`）；零发放须取消（`ZERO_ISSUANCE`）；多行中任一行不足则**整单回滚**（`test_insufficient_second_line_rolls_back_all_posting` 验库存保持 50、无 StockLedger）。✅
- **报损**：`loss`/`scrap`/`recovery`/`found`；`source_loss` 必须指向 `disposal_type='loss'` 同卡、状态 `approved`、卡 `lost`（`check_disposal_ownership`）；在库资产（`in_use`）报损/报废前须先归还（关闭发放关系），否则 `SOURCE_ISSUE_REQUIRED`/`ASSET_MUST_BE_RETURNED`；同一遗失仅可找回一次（`ALREADY_FOUND`，部分唯一索引兜底）；耗材报损仅在审批后扣减（`test_stock_damage_only_deducts_on_approval`）。✅
- **调整**：`count` / `quality_transfer`；过期快照 `STALE_SNAPSHOT`（账面/版本变化 → 整单回滚，`test_count_adjustment_and_stale_same_quantity_new_version`、`test_quality_transfer_rejects_changed_target_version`）；质量转换生成对等借贷台账、总量不变（`test_quality_conversion_has_equal_opposite_ledger_and_no_total_change`）。✅
- **资产编号**：`core.allocate_asset_numbers` 用 `UPDATE tenants SET next_asset_number=next_asset_number+n RETURNING` 一次分配，**禁 MAX+1**，单次 1–1000 校验。✅

### 4.3 Idempotency-Key（§0 / §6 / §8）
`idempotency/service.py`：`OperationRequest` 按 `租户+操作者+operation+key` `get_or_create`；HMAC-SHA256 摘要比对，异摘要 → `IDEMPOTENCY_CONFLICT`(409)；已处理重放返回**存储响应**（`replayed=True`）。`test_execution_replay_different_key_and_invalid_line_identity`：同键两次 → 200/200 且 StockLedger 仅 1 行；异键 → 409。视图层 `Idempotency-Key` 头透传、`Idempotency-Replayed` 回写。✅

### 4.4 租户隔离
`orders.queryset` 强制 `filter(tenant_id=…)`；`header_get` 在租户域内按 pk 取，越域 → 404。`test_reject_cancel_decisions_and_ownership_isolation`：外校 GET 本租户单据 → 404；非 admin GET 入库 → 403。`user` 仅能查/操作本人 `requisition`。✅

### 4.5 自批禁阻 + 审计（§5）
`orders.decide`：`self_approval = applicant_id==actor_id`；若自批且未开 `allow_self_approval` 或未填原因 → `SELF_APPROVAL_FORBIDDEN`（409，整单回滚）；例外路径记录 `self_approved`/`allow_self_approval_snapshot` 并强制原因。`test_scrap_self_approval_guard_and_terminal_freeze`、`test_self_approval_exception_requires_reason_and_records_snapshot` 覆盖。所有写操作落 `AuditLog`（动作/前后变更/原因）。✅

### 4.6 负向（§9）
- **应用层**：`test_orders.py` 26 项中含大量负向断言——坏行原子回滚、跨租户 404、零发放 409、过期快照 409、自批 409、重复快照 422、格式错误 422、转移重复 409、采购退货超额 409、在库资产未归还 409 等。
- **SQL 级**：`sql/test-negative.sql` 21 项断言（含 `stock_ledger` 外键不一致被拒、`inventory_version` 守卫等）全部 PASS、退出码 0。

## 5. 三、P4 与 P5 边界（重要，避免越权验收）

`posting.py` 已落地库存/台账/资产的** Mechanics**（被单据流正确驱动、已被上述测试覆盖），但以下属于 **P5 硬门禁** 的正式验收对象，本报告仅确认"机制已就位、驱动正确"，不替代 P5：

1. **`inventory.version` 自增逻辑**：由 schema 触发器 `inventory_version_guard()`（BEFORE INSERT/UPDATE ON inventory）维护——已确认存在，`move_stock` 不显式 bump（交触发器）。P5 须验证版本单调与维度不可变。
2. **`stock_ledger` 双流水一致性**：consumable 出入对等、balance_after 正确——已测（`test_quality_conversion_has_equal_opposite_ledger_and_no_total_change`），P5 须纳入 13 项对账。
3. **`asset_cards` / `asset_events`**：卡禁删（`asset_card_guard`）、核心字段不可改、事件同卡类型匹配——已测事件链，`asset_card_guard` 属 DB 约束，P5 验。
4. **`reconcile.sql` 13 项内部一致性**：当前 `reconcile` 管理命令与 `reconcile.sql` 在项目中**尚未落地**（属 P7 收尾范畴，不阻塞 P4）。
