# 部署骨架修正说明（2026-11-01）

> 背景：`deploy/` 骨架初版存在两处与"运行身份 / 迁移身份分离"强约束冲突的硬伤，会导致首次云端部署失败。2026-11-01 由控制中枢直接修正 `deploy/docker-compose.yml` 与 `deploy/env.production.template`，无需用户手动改。本文档保留修正内容与原因，供审计追溯。

---

## 修正 1：`docker-compose.yml` 数据库用户歧义

### 原问题
`postgres` 服务：
```yaml
postgres:
  environment:
    POSTGRES_USER: ${DB_USER:-inventory_app}   # ← 跟随 .env 的 DB_USER
```
而 `web` / `worker` / `beat` 用 `env_file: .env` 且**未覆盖 `DB_USER`**。后果：
- 若 `.env` 里 `DB_USER=inventory_app`，则运行时服务以**迁移身份**连库 → `require_runtime` 拦截，`/health/ready/` 返回 503，登录失败。
- 若强行把 `.env` 的 `DB_USER` 改成 `inv_run`，则 PG 初始超级用户变成 `inv_run`，迁移 owner `inventory_app` 丢失，`apply_schema` 无法建库/建角色。

### 修正后
`postgres` 固定为迁移 owner，不随 `DB_USER` 变：
```yaml
  postgres:
    image: postgres:16.15
    environment:
      POSTGRES_DB: ${DB_NAME:-campus_inventory}
      POSTGRES_USER: inventory_app            # ← 固定为迁移 owner，不随 DB_USER 变
      POSTGRES_PASSWORD: ${MIGRATION_DB_PASSWORD:?required}
```
并在 `web` / `worker` / `beat` 三处 `environment:` 中显式锁定运行身份：
```yaml
    environment:
      DB_HOST: postgres
      DB_PORT: "5432"
      DB_USER: inv_run                        # ← 运行身份固定
      DB_PASSWORD: ${RUN_DB_PASSWORD:?required}
      REDIS_URL: redis://redis:6379/0
```

### 配套：`env.production.template` 调整
- 移除原 `DB_PASSWORD=`（单一共享密码）。
- 新增 `MIGRATION_DB_PASSWORD=`（迁移 owner 密码，供 postgres 初始化）。
- 新增 `RUN_DB_PASSWORD=`（运行身份密码，供 web/worker/beat）。
- `DB_USER=inventory_app` 注释改为"仅供 postgres 初始化参考，运行时以 compose 的 inv_run 为准"。

## 说明 2：nginx 未开 TLS（无需改文件，测试期 `DEBUG=true` 绕开）

`nginx.conf` 只 `listen 80`；而应用 `DEBUG=false` 时 `SECURE_SSL_REDIRECT=true` 会把所有 HTTP 请求 301 到 https，nginx 没监听 443 → 页面打不开（无限 301）。

**测试期二选一**：
- 方案 A（推荐测试）：`.env` 设 `DEBUG=true`，关闭 SSL 跳转，直接用 `http://<公网IP>` 访问；
- 方案 B（接近生产）：给 `nginx.conf` 配 `listen 443 ssl` + 证书（自签或 Let's Encrypt），并保留 `DEBUG=false`。

> 结论：第 2 项本质是配置选择而非强制改文件，故未改动 `nginx.conf`。
