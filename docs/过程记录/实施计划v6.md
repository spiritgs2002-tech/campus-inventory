# 学校总务处出入库管理系统 — 实施计划 v6

日期：2026-10-30。配套：schema-v6.sql、v5审核逐项答复与v6验收说明.md、v6-tools目录。

本文是一期唯一规则来源，取代v5正文与末尾补充规则。原始两份审核文件保持不变。本项目独立于校园报修小程序，后续通过资产编号关联维修。

## 1. 范围与交付

一期：Web管理后台、领用人轻端、耗材仓库库存、一物一卡、采购、领用发放、归还、责任人转移、采购退货、报废、遗失与找回、仓库报损、库存调整、质量转换、期初Excel导入、导出及试点。

二期：微信小程序、扫码盘点计划/任务、通知；三期讨论折旧。一期不建部门耗材持有账，不记录发放后的实际消耗，不做批次、有效期、FIFO、成本分摊与折旧。学校在M0确认这些边界；领用统计不应被称作耗用统计。

## 2. 技术、会话与个人信息

Python/FastAPI、SQLAlchemy 2.x、Alembic；Vue3/Vite/Element Plus/Pinia；容器应用与私有对象存储。统一PostgreSQL 16，同一主版本及一致扩展配置用于开发、CI与生产，补丁版本通过部署锁文件记录。该选择是项目运行基线，不是因为num_nonnulls要求PG14，该函数在PG9.6官方文档已存在。

一期不收集手机号。学校代码+用户名登录，用户名租户内唯一；bcrypt密码至少10位，新建/重置后强制改密。失败次数和locked_until存login_throttle，不争用用户业务行锁；租户配置默认5次失败锁15分钟，网关IP限流。失败提示不泄漏账号是否存在。

access只在内存，refresh置httpOnly/Secure/SameSite=Strict、Path=/api/v1/auth cookie。refresh/logout检查Origin白名单、自定义请求头，禁止任意凭据CORS。CSP禁止内联脚本，用户输入转义。每个access带session_id，每次授权检查会话族未撤销、用户与租户状态，不使用auth_version字段；改密、禁用、重置密码事务内撤销所有用户会话族，已有access也失效。

每次刷新产生同family_id的新行，旧行rotated_at表示已消费；revoked_at/revoked_reason只表示登出、禁用、改密或复用撤销。旧token10秒内重现返回REFRESH_ALREADY_ROTATED，前端单飞并共享成功结果；成功响应丢失且无其他结果时重新登录，不无限重试。超窗重现撤销会话族。logout可用有效access的session_id或cookie确定会话族，同Path清除cookie。

会话清理按整个family执行：族内全部token过期超过30天且没有活跃后继时才删除整族，事务内先清parent_session_id再删。不得立即删除刚轮换/撤销的token，否则复用检测失去证据。审计记录保留会话族标识，不保留token明文。

应用audit_logs不保存IP字段；网关为安全防护保留完整IP默认最多7天，限安全运维访问并自动清理，该期限为工程建议，由学校M0确认。学校要求不同期限时走配置评审。IP可能构成个人信息，不不加区分地定性为法律意义上的敏感个人信息。

## 3. 业务规则与单据映射

| 业务 | 单据与规则 |
|---|---|
| 采购 | inbound_orders.purchase；验收后即时执行；耗材按库位/quality入账，资产逐件建卡 |
| 领用 | outbound_orders.requisition；申请不扣库，管理员执行；一次发放，差额关闭并填写原因，零发放应取消；支持复制差额新申请 |
| 归还 | inbound_orders.return；引用已执行发放；累计耗材归还≤实发；资产仅允许未结案关系归还；先插归还明细，再结案旧关系 |
| 转移 | 同transfer_id的return入库和transfer出库；同事务归还再发放，写return/issue两事件；旧关系close_reason=transfer；不额外写第三条状态事件 |
| 采购退货 | outbound_orders.purchase_return；耗材检查来源采购额度及当前可用库存；在库固定资产逐卡退货；只管理员操作 |
| 期初 | inbound_orders.opening，来自file_jobs；期初耗材写流水，期初资产建卡并写事件 |
| 报废 | scrap_orders.scrap；可基于本人未结案发放申请，执行前须归还至in_stock/repair且无责任人 |
| 遗失 | scrap_orders.loss；可从in_stock/repair/in_use核销；在用则结案旧发放为loss，记录核销明细；无原发放不虚造 |
| 找回 | scrap_orders.recovery，引用同卡的原loss明细；审批恢复in_stock/repair，不复活原责任；每次loss只允许一次成功found事件 |
| 耗材报损 | scrap_orders.stock_damage，仅管理员，指定库位、quality和数量；已领用耗材不再次扣库 |
| 调整 | adjustment_orders.count；耗材为观察快照差额，固定资产仅盘盈、逐件quantity=1；固定资产盘亏走loss |
| 盘盈资产入库 | count审批生成inbound_orders.adjustment_gain和入库明细，关联adjustment_item，再建卡写found_gain |
| 质量转换 | adjustment_orders.quality_transfer；一条明细记录源quality、目标to_quality、源方向out与数量；审批写同明细一出一入两笔等量流水，总量不变 |

审批类明确包含scrap/loss/recovery/stock_damage/count/quality_transfer。审批通过与执行同事务；库存不足、快照过期、状态不合法时回滚且保持pending，页面显示失败原因。拒绝/取消写decided_by/at/decision_reason。重新申请复制原内容，不改原单。

quality为available/damaged；领用只扣available。资产入库/找回/盘盈的available映射in_stock，damaged映射repair；两者均无人负责。资产状态转换：创建→in_stock/repair；issue：in_stock→in_use；return：in_use→in_stock/repair；repair_start/finish：in_stock↔repair；scrap：in_stock/repair→scrapped；loss：in_stock/repair/in_use→lost；found：lost→in_stock/repair；purchase_return：in_stock→returned_to_supplier。scrapped与returned_to_supplier终态。

耗材调整记录observed_at、book_qty、counted_qty、quantity、direction及inventory_version。审批锁行检查version与book_qty都一致；期间先出后入即使同量仍过期。quality_transfer同时检查源/目标version。数据库quantity变化触发器自动version+1，服务不得自行递增或改变库存主维度。过期界面提供“重新观察并复制申请”，不自动采信旧实盘值；记录过期率，试点约定当天审批。盘点期间暂停发放留待二期，不以报损+盘盈替代正常质量转换。

发放关系closed_at为空代表未结案；close_reason为return/transfer/loss/purchase_return。采购退货记录创建即结案。转移和归还顺序保证检查旧关系开放后才结案。固定资产实发数必须等于所选卡数，固定资产采购/期初/盘盈建卡数必须等于入库明细quantity。

## 4. 数据库与职责边界

schema-v6.sql共27张表：v5的24张表加login_throttle、attachments、scrap_attachments。file_jobs仍用于导入/导出。附件有租户、对象键、摘要、大小、类型、retention_until、legal_hold、上传人；单据通过同租户关联表引用。存储上传完成后由服务验证内容、摘要、归属再登记，不能只信客户端。证据元数据长期保留，过保留期且无legal_hold时可删除对象并标deleted_at，单据关联保留；存储删除不是数据库事务，需可重试清理任务。

手机号、auth_version和三期折旧字段移除。主数据updated_at记录最近修改，申请保存dept_id快照，历史部门停用保留；部门/供应商名称租户内唯一，由服务统一去首尾空白后写入。资产事件保存目标库位与责任人快照，支持历史查询。

同租户复合外键继续保留；读取仍必须服务端过滤。调整/处置明细冗余头类型，以复合外键与CHECK约束一致性。source_loss必须指向loss且同一资产；found事件部分唯一索引兜底一次找回。

入库头由数据库写created_xid，明细仅同事务插入，不比较系统xmin；禁止创建过程中跨事务或保存点拆分头与明细。即时出库（transfer、purchase_return）统一先pending头→明细/卡片/实发→completed。执行时数据库校验非零发放、差额原因及卡数；pending默认0不要求差额原因。

历史表拒绝UPDATE/DELETE/TRUNCATE，已终结单头/明细冻结；pending申请内容冻结，只允许执行字段变更。入库/发放INSERT有父单守卫。幂等行创建事务可写最终结果，提交后只能在90天后清空response，不得删除身份或修改摘要。SQL补齐常见父单、本人申请、资产责任人、会话用户和审计查询索引。

服务仍承担：物资/源单实际业务类型一致、累计退还额度、租户与角色授权、质量双流水与建卡数、卡片状态变化同步事件、对象存储权限、已提交pending单不追加业务明细。直接UPDATE卡片是否同事务配事件本版以服务断言和对账发现，未实现延迟事件约束；运行角色不是面向用户开放的SQL账号。M3必须测试此残余边界。M0只评估复合外键成本，不以省事为由降级。

## 5. 幂等、锁与并发

operation_requests键域为tenant/actor/operation/key；同操作者同键同摘要重放，不同摘要409。不同操作者是不同请求，不能依赖客户端UUID解决跨操作者业务唯一性；由目标单状态、来源额度、资产关系和file_jobs确认状态兜底。原始操作身份/摘要/业务关联长期保留，90天只清response；之后返回ALREADY_PROCESSED与业务关联。

默认READ COMMITTED；设lock_timeout和statement_timeout，只对死锁40P01/明确锁超时做有限退避重试，复用幂等键；网络响应丢失用幂等查询恢复。占位、业务、最终响应同事务，不允许提交空占位。

锁顺序：操作键→租户行（管理员人数、自批设置/审批、资产编号分配）→按ID排序用户行→目标单据→按类型/ID排序来源明细→按ID排序资产卡→按完整键排序库存行。资产编号用UPDATE tenants SET next_asset_number=next_asset_number+n RETURNING一次分配，禁止MAX+1。

库存缺行先INSERT ON CONFLICT DO NOTHING零行再锁；扣减使用quantity>=数量条件更新并查影响行数；累计退还先锁来源行再统计。停用/降级与发放/转移共用用户锁，锁后重新检查active、资产与pending单；管理员人数先锁租户保证至少一人。login_throttle锁定不改变active，管理员仍可回收、转移、处理停用检查。

## 6. 权限与安全运维

admin执行入出库、归还、转移、审批、调整和人员管理；user只见目录有货/不足、本人申请/资产，可申请领用及本人资产报废/遗失。完整流水、审计只管理员。租户开通/期限通过受控运维，不提供学校管理员跨校接口。

默认禁止自批；开启须原因与审计，审批记录当时快照及self_approved；发放self_issued由实际操作者/申请人一致性CHECK兜底。学校至少两名管理员，单人例外先确认自批规则。

运行/迁移账号分离；v6-tools/grant-runtime.sql可执行授权，verify-runtime.sql断言角色非owner/非超级用户/无继承其他角色、历史表仅读写入、无TRIGGER/TRUNCATE及schema创建能力。使用独立数据库、受控public schema。实际执行并验证权限是M1阻断条件，注释或脚本存在不算通过。

## 7. 页面与操作体验

管理员：仪表盘与低库存、基础资料、采购/发放/归还/转移/采购退货、库存流水、资产事件、处置与调整审批、附件、导入导出、审计、本校设置。领用人：目录、申请、本人资产/申请、报废/遗失、个人中心。

取消/驳回提供携带原内容的新申请；差额再申请只复制未满足量；过期调整要求重新观察确认。冻结单只展示，不以可编辑表单暗示可修改。低库存仅仪表盘，不预留无业务需求的额外通知字段，二期复用safety_stock。

## 8. 导入、切换、清理与恢复

导入物资、期初资产、期初耗材三模板；预览不入账，确认核对文件摘要、模板版本、租户，重新校验并同事务落库；重复编码默认拒绝，不能更新已发生业务的库存。file_jobs确认状态加锁，跨操作者重试同任务也不能重复导入。

切换步骤：确认切换人/窗口→停止旧账写入→导出并校核期初快照与实物→预览修错→确认导入→内部对账0差异且总量与签字快照一致→管理员签字启用新系统→旧账只读封存。失败保持旧账冻结，未启用前可清理隔离试点库重做；启用后纠错走业务单，不双系统同时记账。

导出/二维码临时对象7天、原导入文件30天、完整幂等响应90天；操作身份不删除。附件保留期及legal_hold由学校M0确认写入字段，未确认不允许上线证据清理。附件与普通导出使用不同对象前缀/生命周期，不因导出TTL误删。

优先托管PG PITR，或每日备份+WAL；备份30天、独立权限。目标RPO≤15分钟/RTO≤4小时，试点前实际恢复到指定时点并运行reconcile.sql，记录耗时/查询结果与抽盘签字。对账脚本只检内部一致性，不能替代实物抽盘。审计留存期限M0确认。

## 9. 里程碑与验收

| 阶段 | 必须完成 |

| M2 | 20并发不超发、缺库存行并发入库、同键重放、跨人重复导入防重、调整过期/质量守恒；5000行预览和确认分别≤60秒 |
| M3 | 卡数与建卡数断言、资产状态事件、遗失后禁止归还、一次找回、再次发放、转移与停用竞争、最后管理员保护 |

## 10. 学校决策与迁移边界

M0前确认B1管理员数量/自批、B2资产划分、B3金额必填、B4批次有效期、B5联系方式、B6审计/IP期限、B7责任认定附件/签批/保留年限、B8实物抽盘人员频率、B9不提供部门个人耗用统计。附件模型已提供，B7决定必填和保留策略，不再阻塞表选择。

schema-v6.sql只作M0空库基线与评审，不作现有库升级脚本。生产必须独立Alembic迁移；函数、触发器、角色授权不能依赖autogenerate自动发现。扩展→迁移→收缩，破坏性变更不承诺无损downgrade。已执行业务通过冲正单纠正。

本次交付为计划、DDL和可执行验收辅助脚本；真实PG执行、负向/并发测试与权限验证均需记录实际结果，不能因文件存在标记验收通过。
