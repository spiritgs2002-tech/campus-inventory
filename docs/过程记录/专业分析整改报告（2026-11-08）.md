## 二、逐项核实与整改

### 2.1 免密扫码领用（问题 1）

**核实证据（基线代码）**
- `apps/inventory/pickup.py` 的 `submit()` 在用户未登录时，直接用自报的姓名和工号 `ensure_lightweight_user()`，随后 `pickup_issue()` 在同一事务内完成出库，没有审批。
- 唯一的限制是 `PICKUP_ANONYMOUS_PER_MINUTE`，按**全校**计数（筛选条件 `response__pickup__identity="unverified"`）。没有单次数量上限、没有按工号计数，也没有学校级开关（`Tenant` 只有 `allow_self_approval`）。

**实际修改**
- `campus_inventory/settings.py` 新增以下配置：
  - `ANONYMOUS_SCAN_TENANTS`：`*` 表示全部学校开启，空值或 `none` 表示全部关闭，`1,2` 表示只对列出的租户 ID 开启；格式非法时启动报错。
  - `PICKUP_ANONYMOUS_MAX_QTY`：免密领用单次耗材数量上限，默认 20。
  - `ANONYMOUS_PER_EMPLOYEE_PER_HOUR`：同一工号每类免密操作每小时上限，默认 10。
  - `ANONYMOUS_NEW_IDENTITIES_PER_HOUR`：每校每小时可新登记的免密工号数，默认 30，用来防止轮换工号刷单。
- `apps/inventory/pickup.py`：
  - 新增 `anonymous_enabled()`。它在加租户锁之前和加锁之后各检查一次。
  - 新增 `anonymous_quota()`，统一处理“按工号/小时”和“按学校/分钟”两类计数。计数通过 `OperationRequest.actor` 识别免密身份，并且只统计已有响应的记录，所以当前请求的幂等占位行和同键重放都不计数。
  - `ensure_lightweight_user()` 新增参数 `limit_new`，用于新工号限额。
  - 新增单次数量上限，超限时在创建轻量用户之前就拒绝。
- `apps/inventory/pickup_views.py`：学校未开启免密时，扫码页显示“本校未开启免密扫码登记，请先登录”。

**设计说明**：代码默认值 `*` 保持现有行为，避免升级后已上线学校的扫码功能突然失效。生产模板（`deploy/env.production.template`、`deploy/deploy.sh`、`deploy/deploy.conf.example`）已把这项配置明确写出，并附上风险说明。是否把默认值改为“关闭”需要产品方或学校决策（见 §4）。

### 2.2 免密报修、免密请购限流（问题 2）

**核实证据**：基线的 `apps/repair/services.py` 和 `apps/procurement/services.py` 在免密分支中，除二维码校验外没有任何次数限制。

**实际修改**
- 两个服务的免密分支都加上了 `anonymous_enabled()` 检查，并在加锁后的 `work()` 中调用 `anonymous_quota(p, OPERATION)`。请购的操作名提取为常量 `OPERATION`，值不变，仍是 `procurement.requisition.create`。
- `PICKUP_ANONYMOUS_PER_MINUTE` 的语义从“每校免密领用”扩展为“每校每类免密操作”。领用、请购、报修各自独立计数。
- 管理员运行的 `import_repairs` 导入传 `limit_new=False`，不受新工号限额约束，否则批量导入会被误拦。

### 2.3 免密申请人的通知（问题 3）

**核实结果**：问题部分属实。
- 免密身份的密码哈希带 `!pickup-unverified:` 前缀，**无法登录**；`/s/notifications/` 要求登录，所以通知在开通账号之前确实读不到。
- 但代码里已有恢复路径：管理员在用户管理中为该工号设置密码后，`core.services.save` 会把密码改为 bcrypt 并设置强制改密，该工号即可登录。问题在于这条路径没有任何提示，而且免密请购页的文案“请用同一工号登录以统一查收通知”与实际不符。

**实际修改**
- `apps/procurement/views.py` 和 `templates/procurement/list.html`：管理员在请购列表中会看到免密申请人的标注：“扫码免密登记（工号 X，未核验），无法登录查收站内通知；请线下告知结果，或在用户管理中为该工号设置初始密码后再通知”。
- `templates/procurement/new.html`：修正了误导性文案；提交成功后提示申请人记下单号。
- 新增测试，端到端验证恢复路径：免密请购 → 到货通知 → 管理员设置密码 → 首次登录强制改密 → 登录后能看到 `requisition_arrived` 通知 → 列表标注消失。

**没有做的**：没有提供免登录查看通知的通道，因为那会让知道工号的人看到别人的通知。

### 2.5 功能空白（问题 5）

| 子项 | 处理 | 说明 |
|---|---|---|
| 报表/导出 | **已实现** | 新增 `apps/inventory/exports.py`，提供 `/stock/export.csv`、`/stock/ledger/export.csv`、`/assets/export.csv`，仅管理员可用。直接复用列表页的授权查询和筛选（`queries.*` 新增 `paginate` 注入参数，原分页行为不变）。带 UTF-8 BOM，单次最多 50000 行，以 `= + - @` 等开头的非数字单元格会被转义，防止公式注入。响应为 `no-store`，导出操作写入应用日志。列表页有“按当前筛选导出 CSV”链接。 |
| 期初导入 | **已实现** | 新增 `apps/inventory/opening_import.py` 和 `/inbound/import/` 页面（导航中的“期初导入”）。CSV 支持 UTF-8 或 GBK，列为物资编码、库位、数量，可选质量和单价。先对全部行做校验，有错误就逐行报告且不写入任何数据。“预检”会完整执行一遍入库服务后回滚；“正式导入”按每 50 行（或每 1000 件固定资产）拆成多张 `opening` 入库单，整份文件在同一事务内，任一张失败全部回滚。同一文件换幂等键再次导入会被拒绝。**单文件上限定为 1000 行**：本次实测 5000 行耗时约 40 秒，接近 gunicorn 和 nginx 的 60 秒超时。 |
| 低库存主动通知 | **未闭环** | `notifications.type` 有 DDL CHECK，只允许 `requisition_arrived` 和 `requisition_rejected`。新增通知类型需要按 SQL-first 约定另建迁移、更新权威源 schema 并重新做 G0 门禁，超出本次范围。目前可以用 `/stock/?low=true` 筛选，并通过新的导出功能获取清单。 |
| 报修联动资产状态 | **未闭环（设计取舍）** | README P8c 明确写明“工单不自动改变资产状态”，`verify_p8c` 也断言“asset repair hook remains disabled”。是否联动需要业务方决定，本次不改。 |

### 2.6 可维护性（问题 6）

- **`SECURE_PROXY_SSL_HEADER`：已整改**。现在只有设置 `TRUST_X_FORWARDED_PROTO=true` 时才开启，默认关闭。以下部署入口都已同步：
  - `deploy/docker-compose.yml`：web 服务固定设为 `"true"`（compose 中 web 只经 nginx 访问，而 nginx 会覆盖 `X-Forwarded-Proto`）。
  - `deploy/env.production.template`：`true`，用于 systemd 和云上部署。
  - `deploy/deploy.sh`：写出 `true`。
  - `django/.env.example`：`false`。
  - 文档：腾讯云部署方案、部署选型总览、实测清单、云端手册。
- **⚠ 升级注意**：已有部署如果使用自己维护的环境文件，升级后必须补上 `TRUST_X_FORWARDED_PROTO=true`，否则在 nginx/CLB 后面会出现 HTTPS 跳转死循环。
- **根目录文档杂乱、`models.py`/`orders.py` 过大：未闭环**。这两项是组织和重构建议，不是缺陷。挪动文档会破坏现有链接和审计引用；拆分大文件风险高、收益低，不宜和功能整改放在一起。

## 四、尚未闭环项

1. **免密开关默认值**：代码默认 `*`，为了兼容。安全上更好的做法是默认关闭，但这会改变已上线学校的行为，需要产品方或学校书面决定。
2. **低库存通知、报修完成通知**：需要新增 DDL 迁移来放宽 `notifications.type` 的 CHECK 约束。
3. **报修联动资产状态**：属于业务设计取舍，需要决策。
4. **期初导入跨文件去重**：同一份文件不会重复导入，但拆成多个文件时，同一物资/库位/质量重复出现不会被检测，需要人工避免。
5. **导出操作只记应用日志，没有写 `AuditLog`**：现有 `core.audit` 面向写操作；如需正式审计导出，需另行设计。
6. **文档整理、大文件拆分**：属于建议，暂不执行。

## 五、本次发现的原有问题（未修改，供决策）

1. **CI 第一步在 HEAD 上就会失败**：在 `9e99df5` 的干净副本上运行 `verify_ci_delivery.py`，输出 `CI_TEMPLATE_DRIFT: canonical workflow and portable copy differ`。原因是上次提交修改了 `.github/workflows/ci.yml`，但没有同步可移植模板。
2. **CI 的身份配置与测试本身不一致**：
   - 以 `inventory_ci` 身份运行时，有 17 个测试在基线上就失败（13 个需要表 owner 来注入数据损坏；`grant-ci-test.sql` 授予了 tenants 写权限，与断言“运行身份不能改 tenants”冲突，等等）。
   - CI 中 `verify_p7`/`p8a`/`p8b`/`p8c`/`readiness` 也以 `inventory_ci` 运行，而这些脚本需要 CREATEDB 来创建临时库。本次复现为 `permission denied to create database`；改用 DBA 管理连接后全部通过（见 §三）。
   - 远端 Actions 的运行记录本次没有查看，以上是本地按 CI 配置复现的结果。
