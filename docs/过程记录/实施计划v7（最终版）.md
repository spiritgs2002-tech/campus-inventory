## 0. 终审结论与准入清单

### 0.1 终审判定

v6 的**设计质量已达可实施水准**，但必须说清三者的边界：

- **由数据库强制**：多租户复合外键、触发器冻结与 append-only、幂等键唯一、入库头/明细同事务 xid 守卫、库存 version 自增与维度不可变、完成态差额原因与卡数校验、附件元数据不可改。
- **由服务层保证并以测试覆盖**：快照 version 与 book_qty 一致性（P1-4）、跨操作者来源额度、卡片状态与事件同事务（延迟约束未实现，残余风险）。
- **仅由对账发现**：reconcile.sql 的 13 项检查；对账不替代实物抽盘。

### 0.4 【P2 中】随实现消化

- **P2-1**：`scrap_attachments` 因复用 `protect_order_line`，DELETE 一律拒绝 → **证据附件任何阶段不可删**，连 pending 误传也只能取消整单。**✅ v7 已决策并落地**：pending 且未裁决时允许撤回（`evidence_line_guard` 放行 DELETE）；已裁决后仅可追加，对象存储清理由服务同步执行。

- **P2-4**：`operation_requests.created_xid` 列默认与 `xid_stamp` 触发器重复赋值（`inbound_orders` 同），**✅ v7 已落地**：`schema-v7.sql` 已移除 `operation_requests`/`inbound_orders` 的列默认，仅保留 `xid_stamp` 触发器。

### 0.5 【A1 架构决策·须裁决】技术栈与项目宪法冲突

- **本计划 §2 声明**：Python/FastAPI + SQLAlchemy 2.x + Alembic + Vue3/Vite/Element Plus/Pinia + 容器与私有对象存储。
- **项目宪法 `ARCHITECTURE.md` 硬约束**：Python 3.13 + **Django 5** + PostgreSQL 16 + Celery/Redis + **Django Templates/Alpine.js/HTMX/Bootstrap 5**，且资产/总务归属 `apps/asset`。

**二者不可并存，须裁决其一：**

| 方案 | 含义 | 代价 |
|---|---|---|
| **A1-a** | 库存系统**确认为独立产品**，不受宪法技术栈约束 | 需在 `ARCHITECTURE.md` 明确标注例外，否则未来集成 `apps/asset` 必然返工；两套权限/审计体系并存 |
| **A1-b** | 库存系统**归入校园 SaaS**，改用 Django 栈 | **按「SQL 优先 + Django 只做 ORM 读写」重估**：Django 的 `ForeignObject` 不创建外键约束与索引、且属不受弃用策略保护的内部 API，因此 27 张表的**复合外键与 32 个触发器无法由 Django Model 表达，必须手写 `RunSQL` 迁移**——即 schema-v7.sql 仍是规则来源，Django 只承担读写与权限外壳；此外须**先选定隔离模型**（本项目现行为「复合外键 + 服务过滤」，宪法为「tenant_id + RLS」，二者不同，见决策 D3）。工程量集中在迁移封装与权限/审计体系对齐，收益是体系统一 |

> **✅ D1 已裁决（2026-10-31）**：用户确认**维持项目宪法 `ARCHITECTURE.md`**，即 A1-b——库存系统归入校园 SaaS，采用 Django 5 + PostgreSQL 16 栈。schema-v7.sql 仍为 SQL 规则来源，Django 仅承担 ORM 读写与权限/审计外壳（复合外键与 32 个触发器须经手写 `RunSQL` 迁移，无法由 Model 生成）。原默认建议 A1-a 作废。D2（隔离模型：本项目复合外键+服务过滤 vs 宪法 tenant_id+RLS）仍待与宪法对齐，但实现侧已按复合外键+服务过滤落地，不阻塞开发。

## 2. 技术、会话与个人信息

- 栈：**已裁决 D1 = A1-b（归入校园 SaaS，Django 栈）**。遵循项目宪法 `ARCHITECTURE.md`：**Django 5 + psycopg3 + PostgreSQL 16 + Celery/Redis + Django Templates / Alpine.js / HTMX / Bootstrap 5**；资产/总务归属 `apps/asset`。SwiftUI 桌面小组件、FastAPI、Vue3、SQLite(WAL) **均不适用**（本次裁决明确排除），其 JWT/RBAC 设计思路已转化为 Django 形态（见 `开发规范（Django+PG）.md`）。统一 **PostgreSQL 16**；开发/CI/生产保持同一主版本与一致扩展配置，补丁版本通过部署锁文件记录。
- **规则回归补遗（A10）**：以下规则自 v5/v6 继承，v7 首版整理时漏列，在此恢复并纳入测试：①租户开通与期限调整只走受控运维，不提供学校管理员跨校接口；②二维码 token 用 ≥128 位随机串，不得作为免登录凭证；③租户隔离测试必须覆盖原生 SQL、后台任务、批量导入、对象存储下载四条通路；④导出按角色分级授权；⑤所有写命令必须带 `Idempotency-Key`，服务端按租户+操作者键域处理。
- **版本下限**：支持下限与测试基线统一为 **PostgreSQL 16**（PG13 已于 2025 年底结束官方支持，不作为支持矩阵）。技术下限为 PG13（因 `pg_current_xact_id()` 自 13 提供），仅作背景说明。
- 会话：access 仅内存；refresh 置 httpOnly/Secure/SameSite=Strict、Path=/api/v1/auth cookie。refresh/logout 检查 Origin 白名单与自定义请求头，禁止任意凭据 CORS。CSP 禁内联脚本，用户输入转义。
- 撤销：每个 access 带 `session_id`，每次授权检查**会话族未撤销 + 用户/租户状态**（不设 `auth_version`：撤销整族在语义上等价于版本号跳跃，族撤销模型已覆盖失效需求）。改密/禁用/重置密码在事务内撤销该用户全部会话族。
- **会话检查的实现约束（B9）**：上述三项检查必须在**一条联查**中完成（`auth_sessions` JOIN `users` JOIN `tenants`，按族聚合），不得拆成三次往返。允许缓存，缓存键为**会话族 ID**；失效点为：族撤销、改密、用户停用/启用、租户状态或到期日变更、管理员强制下线。**缓存最长 60 秒且必须在上述事件时主动失效**；不缓存则每次联查，M2 用压测决定是否启用缓存。
- 刷新：每次产生同 `family_id` 新行，旧行 `rotated_at` 表示已消费；`revoked_at`/`revoked_reason` 仅表示登出/禁用/改密/复用撤销。旧 token 10 秒内重现返回 `REFRESH_ALREADY_ROTATED`，前端单飞共享结果；响应丢失且无其他结果时重新登录，不无限重试；超窗重现撤销整族。
- **会话清理（P1-2）**：按整族执行——族内全部 token 过期超 30 天且无活跃后继才删除，事务内先清 `parent_session_id` 再删。**必须提供可重试实现**（函数或应用层任务），不得只留文字。审计记录会话族标识，不保留 token 明文。
- 个人信息：**一期不收集手机号**。租户 code + 用户名登录，用户名租户内唯一；bcrypt 至少 10 位，新建/重置后强制改密。失败计数与 `locked_until` 存 `login_throttle`（不争用用户业务行锁）；默认 5 次失败锁 15 分钟，网关 IP 限流；失败提示不泄漏账号是否存在。
- IP：应用 `audit_logs` **不存 IP**；网关为安全防护保留完整 IP 默认 ≤7 天，限运维访问并自动清理，期限由学校 M0 确认。IP 可能构成个人信息，但不不加区分地定性为法律意义上的敏感个人信息。

## 3. 业务规则与单据映射

| 业务 | 单据与规则 |
|---|---|
| 采购 | `inbound_orders.purchase`；验收后即时执行；耗材按库位/quality 入账，资产逐件建卡 |
| 领用 | `outbound_orders.requisition`；申请不扣库，管理员执行；一次发放，差额关闭并填原因，零发放应取消；支持复制差额新申请 |
| 归还 | `inbound_orders.return`；引用已执行发放；累计耗材归还 ≤ 实发；资产仅允许未结案关系归还；**先插归还明细，再结案旧关系** |
| 转移 | 同 `transfer_id` 的 return 入库 + transfer 出库；同事务归还再发放，写 return/issue 两事件；旧关系 `close_reason=transfer`；不额外写第三条状态事件 |
| 采购退货 | `outbound_orders.purchase_return`；耗材检查来源采购额度及当前可用库存；在库固定资产逐卡退货；仅管理员 |
| 期初 | `inbound_orders.opening`，来自 `file_jobs`；期初耗材写流水，期初资产建卡并写事件 |
| 报废 | `scrap_orders.scrap`；可基于本人未结案发放申请，执行前须归还至 `in_stock`/`repair` 且无责任人 |
| 遗失 | `scrap_orders.loss`；可从 `in_stock`/`repair`/`in_use` 核销；在用则结案旧发放为 loss；无原发放不虚造 |
| 找回 | `scrap_orders.recovery`，引用同卡原 loss 明细；审批恢复 `in_stock`/`repair`，不复活原责任；每次 loss 只允许一次成功 found |
| 耗材报损 | `scrap_orders.stock_damage`，仅管理员，指定库位/quality/数量；已领用耗材不再次扣库 |
| 调整 | `adjustment_orders.count`；耗材为观察快照差额，固定资产仅盘盈、逐件 quantity=1；固定资产盘亏走 loss |
| 盘盈资产入库 | count 审批生成 `inbound_orders.adjustment_gain` 与入库明细，关联 adjustment_item，再建卡写 found_gain |
| 质量转换 | `adjustment_orders.quality_transfer`；一条明细记录源 quality、目标 `to_quality`、方向 out 与数量；**审批写同一明细一出一入两笔等量流水**，总量不变 |

- 审批类含：`scrap` / `loss` / `recovery` / `stock_damage` / `count` / `quality_transfer`。**审批通过与执行同事务**；库存不足、快照过期、状态不合法则回滚并保持 pending，页面显示失败原因。拒绝/取消写 `decided_by/at/decision_reason`。重新申请复制原内容，**不改原单**。
- quality 为 `available`/`damaged`；**领用只扣 available**。资产入库/找回/盘盈的 available 映射 `in_stock`，damaged 映射 `repair`，两者均无人负责。
- 资产状态机：创建→`in_stock`/`repair`；issue：`in_stock`→`in_use`；return：`in_use`→`in_stock`/`repair`；repair_start/finish：`in_stock`↔`repair`；scrap：`in_stock`/`repair`→`scrapped`；loss：`in_stock`/`repair`/`in_use`→`lost`；found：`lost`→`in_stock`/`repair`；purchase_return：`in_stock`→`returned_to_supplier`。`scrapped` 与 `returned_to_supplier` 为终态。
- 耗材调整记录 `observed_at`、`book_qty`、`counted_qty`、`quantity`、`direction` 及 `inventory_version`。**审批锁行检查 version 与 book_qty 都一致**；期间先出后入即使同量仍判过期；`quality_transfer` 同时检查源/目标 version。数据库 quantity 变化时触发器自动 `version+1`，**服务不得自行递增或改变库存主维度**。过期界面提供"重新观察并复制申请"，不自动采信旧实盘值；记录过期率，试点约定当天审批。盘点期间暂停发放留待二期。**不得以报损 + 盘盈替代正常质量转换**。
- 发放关系 `closed_at` 为空代表未结案；`close_reason` ∈ return/transfer/loss/purchase_return。采购退货记录创建即结案。固定资产实发数必须等于所选卡数；固定资产采购/期初/盘盈建卡数必须等于入库明细 quantity。

## 4. 数据库与职责边界

- `schema-v7.sql` 共 **27 张表**（v5 的 24 张 + `login_throttle`、`attachments`、`scrap_attachments`）。`file_jobs` 仍用于导入/导出。
- 附件含租户、对象键、sha256、大小、类型、`retention_until`、`legal_hold`、上传人；单据经同租户关联表引用。**上传完成后由服务校验内容/摘要/归属再登记，不能只信客户端**。证据元数据长期保留；过保留期且无 `legal_hold` 时可删对象并标 `deleted_at`，单据关联保留；**对象删除不是数据库事务，需可重试清理任务**。
- 移除手机号、`auth_version`、三期折旧字段。主数据 `updated_at` 记录最近修改；申请保存 `dept_id` 快照，历史部门停用保留；部门/供应商名称租户内唯一，由服务统一去首尾空白后写入。资产事件保存目标库位与责任人快照。
- **同租户复合外键 + 服务端过滤双保留**；调整/处置明细冗余头类型，以复合外键与 CHECK 保证一致性；`source_loss` 必须指向 loss 且同一资产；found 事件用部分唯一索引兜底一次找回。
- 入库头由数据库写 `created_xid`，明细仅同事务插入，不比较系统 `xmin`；禁止创建过程中**跨事务**拆分头与明细（保存点不破坏该守卫——`pg_current_xact_id()` 返回顶层事务 ID，M0 须用测试验证）。即时出库（transfer、purchase_return）统一先 pending 头 → 明细/卡片/实发 → completed。pending 默认 0 不要求差额原因，**completed 时由数据库校验**非零发放、差额原因及卡数。
- 历史表拒绝 UPDATE/DELETE/TRUNCATE，已终结单头/明细冻结；pending 申请内容冻结，只允许执行字段变更。入库/发放 INSERT 有父单守卫。幂等行创建事务可写最终结果，提交后仅能在 90 天后清空 `response`，不得删除身份或修改摘要。
- **服务仍承担**（未下沉到 DB）：物资/源单实际业务类型一致、累计退还额度、租户与角色授权、质量双流水与建卡数、卡片状态变化同步事件、对象存储权限、已提交 pending 单不追加业务明细。直接 UPDATE 卡片是否同事务配事件，本版以服务断言 + 对账发现，**未实现延迟事件约束**，列为残余风险，M3 必须测试。
- M0 **只评估复合外键成本，不以省事为由降级**。

**v7.2 新增/强化的数据库守卫**（均在真实 PG16.15 上有正负用例，见 `v7-tools/test-negative.sql`，共 21 项）：

| 守卫 | 强制内容 | 对应 |
|---|---|---|
| `asset_card_guard` | 资产卡永不物理删除；`asset_no`/`item_id`/`item_type`/`source_inbound_item_id`/`qr_token`/`original_value`/`purchase_date` 不可改；仅 `status`/`location_id`/`responsible_user_id` 可变 | N7 |
| `loss_type` 生成列 + 四列外键 | 结案原因 `loss` 只能指向 `disposal_type='loss'` 且**同卡**的报损明细 | N5 |
| `scrap_event_type` 生成列 + 四列外键 | 事件的 `scrap`/`loss`/`found` 只能引用同卡、且处置类型分别为 `scrap`/`loss`/`recovery` 的明细 | N8 |
| `stock_ledger` 报损三列外键 | 流水物资必须与报损明细物资一致（固定资产报损不产生流水，`stock_ledger` 仅 consumable） | N9 |
| `attachments` 租户内唯一 | `object_key` 改 `UNIQUE(tenant_id,object_key)`，避免跨租户键探测；**服务须强制键带租户前缀** | N10 |
| 孤儿附件可提前标记删除 | 未被处置单关联的附件（误传）可在保留期届满前置 `deleted_at`；已关联附件仍受保留期约束；**已标记删除的附件不得再被关联** | N6 |
| `legal_hold` 单向 | 合规保全只能 false→true，**解除保全只能走受控运维**（直接 UPDATE 被拒） | N3/B4 |
| `scrap_attachments` 权限收窄 | 运行角色**有 DELETE、无 UPDATE**；是"业务表不可 DELETE"的唯一例外，且窗口由 `evidence_line_guard` 收窄到父单 pending 且未决策 | N6/B5 |

> **生成列与 BEFORE 触发器的交互（新增硬性约束）**：BEFORE 触发器中 `to_jsonb(NEW)` 的生成列值**尚未计算（为 NULL）**，而 `to_jsonb(OLD)` 是已计算值。
> 凡用整行 jsonb 比较的触发器，必须把生成列**显式排除**，否则会恒判为"行已变更"。
> 实例：新增 `loss_type` 后 `close_asset_issue_once` 曾被破坏——**结案永远被拒**（错误为 `only one closure append is permitted`），已修复并纳入负向测试。
> **今后每次新增生成列，必须复查同表所有 BEFORE 触发器。**

## 5. 幂等、锁与并发

- `operation_requests` 键域 `tenant/actor/operation/key`。**列语义澄清**：`created_at` 为占位创建时间；`completed_at DEFAULT now()` 在占位时即写入，因此它**不是业务完成时间**——业务完成由 `business_refs` 与 `completed_at` 显式更新表达。90 天清理逻辑必须以**最后一次更新为准**，不得把默认误读为完成时间（N11）。同操作者同键同摘要重放，不同摘要 409。**不同操作者是不同请求**，不能依赖客户端 UUID 解决跨操作者业务唯一性；由目标单状态、来源额度、资产关系和 `file_jobs` 确认状态兜底。原始身份/摘要/业务关联长期保留，90 天只清 `response`；之后返回 `ALREADY_PROCESSED` 与业务关联。
- 默认 **READ COMMITTED**；设 `lock_timeout` 与 `statement_timeout`，**只对死锁 40P01 / 明确锁超时做有限退避重试**（复用幂等键）；网络响应丢失用幂等查询恢复。占位、业务、最终响应同事务，**不允许提交空占位**。
- **统一锁顺序**：操作键 → 租户行（管理员人数、自批设置/审批、资产编号分配）→ 按 ID 排序用户行 → 目标单据 → 按类型/ID 排序来源明细 → 按 ID 排序资产卡 → 按完整键排序库存行。资产编号用 `UPDATE tenants SET next_asset_number=next_asset_number+n RETURNING` 一次分配，**禁止 MAX+1**。
- 库存缺行先 `INSERT ... ON CONFLICT DO NOTHING` 零行再锁；扣减使用 `quantity>=数量` 条件更新并检查影响行数；累计退还先锁来源行再统计。停用/降级与发放/转移共用用户锁，锁后重新检查 `active`、资产与 pending 单；管理员人数先锁租户保证至少一人。`login_throttle` 锁定**不改变 `active`**，管理员仍可回收、转移、处理停用检查。

## 6. 权限与安全运维（RBAC）

| 角色 | 权限 |
|---|---|
| **admin（管理员）** | 入库/出库、归还、转移、审批、调整、人员管理；完整流水与审计可见 |
| **user（领用人）** | 目录有货/不足可见、本人申请与本人资产；可申请领用、发起本人资产报废/遗失 |

- **默认禁止自批**；开启须原因与审计，审批记录当时快照及 `self_approved`；发放 `self_issued` 由"实际操作者=申请人"CHECK 兜底。学校须至少两名管理员，单人例外须先确认自批规则。
- **运行/迁移账号分离**。使用 `v7-tools/grant-runtime.sql` 授权、`verify-runtime.sql` 断言。运行时角色必须：非表 owner、非超级用户、无角色继承、无 TRIGGER/TRUNCATE、无 schema CREATE。使用独立数据库与受控 public schema。
- **M1 硬性阻断**：实际执行授权脚本并通过断言，**注释或脚本存在不算通过**；实际登录角色的额外成员权限也必须验证。
- verify 覆盖要求见 §0.3 P1-1（必须补 DELETE/UPDATE 负向断言）。

## 7. 页面与操作体验

- **管理员**：仪表盘与低库存、基础资料、采购/发放/归还/转移/采购退货、库存流水、资产事件、处置与调整审批、附件、导入导出、审计、本校设置。
- **领用人**：目录、申请、本人资产/申请、报废/遗失、个人中心。
- 取消/驳回提供**携带原内容的新申请**；差额再申请只复制未满足量；过期调整要求重新观察确认。冻结单只展示，**不以可编辑表单暗示可修改**。低库存仅仪表盘；不预留无业务需求的通知字段，二期复用 `safety_stock`。

## 8. 导入、切换、清理与恢复

- **导入**：物资、期初资产、期初耗材三模板；**预览不入账**；确认时核对文件摘要、模板版本、租户，重新校验并同事务落库；重复编码默认拒绝，不能更新已发生业务的库存。`file_jobs` 确认状态加锁，跨操作者重试同任务也不重复导入。
- **切换步骤**：确认切换人/窗口 → 停止旧账写入 → 导出并校核期初快照与实物 → 预览修错 → 确认导入 → **内部对账 0 差异且总量与签字快照一致** → 管理员签字启用新系统 → 旧账只读封存。失败保持旧账冻结，未启用前可清理隔离试点库重做；启用后纠错走业务单，**不双系统同时记账**。
- **生命周期**：导出/二维码临时对象 7 天、原导入文件 30 天、完整幂等响应 90 天；**操作身份不删除**。附件保留期及 `legal_hold` 由学校 M0 确认写入字段，未确认**不允许上线证据清理**。附件与普通导出使用不同对象前缀/生命周期，不因导出 TTL 误删。
- **备份恢复**：优先托管 PG PITR，或每日备份 + WAL；备份 30 天、独立权限。目标 **RPO ≤15 分钟 / RTO ≤4 小时**。试点前**实际恢复到指定时点并运行 `reconcile.sql`**，记录耗时、查询结果与抽盘签字。`reconcile.sql` 只检内部一致性，**不能替代实物抽盘**。审计留存期限由 M0 确认。
