## 0. 已确认的关键决策（用户拍板）
1. **微信集成深度**：仅当扫码器。二维码 = 物品网址，微信扫码在其内置浏览器打开移动网页；**不接微信 SDK / 公众号 OAuth**，零认证成本。
2. **教师身份**：双轨。已登录 `user`（领用人）账号可一键操作；未登录也可在扫码/申请页填「姓名+工号」登记（系统留痕，无密码）。
3. **通知渠道**：仅系统内消息（MVP）。邮件/短信/企微后续可追加，本阶段不做。
4. **报修范围**：通用报修工单（报修人 + 物品/场地/设备 + 故障描述 + 照片 + 派单 + 进度跟踪），新建独立模块。

## 1. 目标与范围
为校园库存 SaaS 增加三条面向**教师/领用人**的自助链路，与现有总务处（admin）后台协同：
- **A. 扫码一键领用**：教师用微信扫物品二维码 → 移动网页 → 确认领用（登录或填姓名+工号）→ 自动生成出库/领用单。
- **B. 库存查看 + 请购申请流程**：教师登录后浏览库存 → 缺货可提交请购申请 → 总务主任审批 → 采购到货后入库增库存 → **系统站内通知申请人** → 教师来领取（扫码或手工）。
- **C. 通用报修工单**：教师上报故障（物品/场地/设备 + 照片）→ 总务处派单/跟踪 → 完成。

## 2. 现状复用清单（避免重复造轮子）
基于代码实测，以下**已存在**，本方案在其上扩展而非重建：
- **角色**：`admin`（总务/管理员）+ `user`（领用人/教师）已存在；`read_views` 已对 `user` 开放库存查看。
- **资产二维码**：`AssetCard.qr_token` 已存在；`/assets/scan/<token>/` 已可扫码打开资产页（`html_read`，需登录）。
- **订单与审批骨架**：`orders.py` 已有 `applicant_id`/`recipient_id` + 状态流（pending→approved/rejected→completed/cancelled）+ `decision_fragment` 审批 UI；入库(`InboundOrder`)/出库(`OutboundOrder`)/报废/调整单据齐全。
- **资产维修状态**：`api_repair`/`html_repair` 已有 `repair_start`/`repair_finish`（固定资产维修状态切换）。
- **附件/照片**：`apps/attachments` 已存在（中间件/视图），报修照片直接复用。
- **前端**：Django 模板 + Bootstrap5（含 `viewport` 自适应），移动端可用。

## 3. 新增 / 改造模块

### M1 扫码一键领用（核心）
- **新增二维码覆盖耗材**：`catalog.Item` 新增 `qr_token`（32 字节随机，与 `AssetCard.qr_token` 同机制）；固定资产沿用已有 `qr_token`。统一一张「二维码映射表」或两表各自 token 均可，建议加 `UNIQUE` 约束。
- **新增移动领用页**：`GET /s/pickup/<token>/`（server-rendered 移动页，微信浏览器兼容，无重 JS）展示物品名/位置/当前库存（耗材）或资产信息；「确认领用」按钮。
- **双轨身份领用接口**：`POST /api/v1/pickup/<token>/`
  - 已登录 `user`：用会话身份，`recipient_id` = 当前用户。
  - 未登录：请求体含 `name` + `employee_no`，系统建/查一个轻量领用人记录（或写入 `recipient_name` 字段），留痕。
  - 成功后生成 `OutboundOrder`（类型=领用，来源=scan）及 `OutboundItem`/`OutboundAsset`，并写 `AssetEvent`（如资产）。
- **约束**：领用接口必须以**运行身份 `inv_run`** 走 DB（`require_runtime` 守卫），不得用迁移身份。

### M2 库存查看移动增强
- 现有 `html_read`/`api_read` 已对 `user` 开放，基本可用。本阶段仅做：
  - 移动端库存浏览页 `/s/inventory/`（列表+搜索，微信浏览器友好）；
  - 缺货项旁边加「申请」按钮，跳转 M3 申请页。

### M3 请购申请 + 审批 + 采购入库联动（新 app `procurement`）
- **新增模型 `Requisition`**（建议独立 app `apps/procurement`，或并入 `inventory`）：
  `tenant_id, applicant_id(可空), applicant_name, applicant_no, item_id, qty, reason, status(pending/approved/rejected/cancelled/purchased), approved_by, inbound_order_id, created_at, updated_at`。
- **教师端**：`GET /s/requisition/new/?item=<pk>` + `POST /api/v1/requisition/` 提交申请（双轨身份同 M1）。
- **审批端**：admin 在 `decision` 视图审批（复用/扩展现有 `decision_fragment`）；批准后可一键「标记采购完成并入库」→ 生成 `InboundOrder` 增库存，并回填 `requisition.inbound_order_id`、状态=`purchased`。
- **联动通知**：入库完成触发 M4 通知（见下）。

### M4 站内通知（新 app `notifications`）
- **新增模型 `Notification`**：`tenant_id, recipient_user_id(可空), recipient_name, type, title, body, ref_type, ref_id, is_read, created_at`。
- **接口**：`GET /api/v1/notifications/`（列表）、`POST /api/v1/notifications/<id>/read/`；`base.html` 加铃铛图标显示未读数。
- **触发点**：M3 入库完成 → 给申请人创建「您申请的 XX 已到货，请前来领取」通知；未来可扩展其他触发。

### M5 通用报修工单（新 app `repair`）
- **新增模型 `RepairTicket`**：`tenant_id, reporter_user_id(可空), reporter_name, reporter_no, target_type(asset/item/location), target_id, description, photo_attachment_id(复用 attachments), status(pending/dispatched/repairing/done/cancelled), assigned_to(可空 user), created_at, updated_at`。
- **教师端**：`GET /s/repair/new/` + `POST /api/v1/repair/`（双轨身份；照片走 `attachments` 上传）。
- **处理端**：admin 列表/详情/派单(`assigned_to`)/更新状态；状态机：`pending→dispatched→repairing→done`，可 `cancelled`。
- **与资产维修联动（可选）**：当 `target_type=asset` 且工单 `done` 时，可触发现有 `repair_start/finish` 资产事件，保持资产维修状态一致。

### M6 二维码标签生成与打印
- **新增依赖**：`qrcode[pil]`（加入 `requirements.txt` + `uv.lock`，走 B9 锁定流程）。
- **新增**：二维码 PNG 端点 `GET /api/v1/qr/<token>/png`（运行身份可读）与 admin「打印标签」页，供总务处批量生成资产/耗材二维码贴纸。

## 4. 角色与权限
- 维持 `admin` / `user` 两角色；`user` 已可查看库存、提交领用/申请/报修。
- 报修派单 `assigned_to` 可指向某 `user`（未来可加 `maintainer` 角色，本阶段不强制）。
- 所有写操作继续走 `require_role` + `require_runtime` 守卫。

## 5. 数据模型变更方式（严守项目宪法）
- **SQL-first**：所有 DDL/触发器/函数/授权**手写 RunSQL 迁移**，严禁 Django autogenerate；先更新 `schema-v7.sql` 规则源（新增表/函数），再写 `migrations/00xx_sql.py` 的 `RunSQL`。
- 新增表：`catalog.item.qr_token`、`procurement_requisition`、`notifications_notification`、`repair_repairticket`。
- 保持「复合外键 + 服务过滤」隔离模型（与宪法 D3 现状一致，不阻塞）。

## 7. 验收标准（V 系列）
- **V-scan-1**：为某资产与某耗材生成二维码 PNG，微信扫码打开移动领用页（无需登录可见）。
- **V-scan-2**：已登录 `user` 扫码 → 一键确认 → `OutboundOrder`（来源=scan，recipient=该用户）生成，库存/资产事件正确。
- **V-scan-3**：未登录扫码 → 填姓名+工号 → 领用单生成且 `recipient_name` 留痕。
- **V-inv-1**：`user` 移动端浏览库存并可搜索；缺货项有「申请」入口。
- **V-req-1**：教师提交请购申请（双轨身份），状态=pending。
- **V-req-2**：admin 审批通过/驳回两条路径均正确。
- **V-req-3**：审批通过后「采购到货入库」→ 库存增加 + `requisition` 状态=`purchased` + 回填 `inbound_order_id`。
- **V-notify-1**：申请人登录后铃铛可见「XX 已到货」通知，可标记已读。
- **V-repair-1**：教师提交报修工单（含照片上传），状态=pending。
- **V-repair-2**：admin 派单/更新状态至 done。
- **V-repair-3**：报修人可查看自己工单状态。
- **回归**：全量 Django 测试（当前 160）+ 各阶段新增测试，CI `ci.yml` 门禁保持全绿；`check --deploy` 0 问题；G0 无回归。

## 8. 关键技术注意
- **微信浏览器兼容**：页面 server-rendered 表单为主，避免依赖被微信浏览器拦截的特性（如某些 push API）；Bootstrap5 已含 viewport，移动端自适应 OK。
- **双轨身份落库**：未登录领用/申请/报修必须有 `name+no` 留痕字段，禁止匿名写入业务单。
- **运行/迁移身份分离**：所有运行期写接口用 `inv_run`；建表/迁移用 `inventory_app`；测试沿用 CI 的 `postgres` 超级用户配置。
- **SQL-first 红线**：DDL 改动一律手写 RunSQL + 同步 `schema-v7.sql`。
- **依赖锁定**：新增 `qrcode[pil]` 须同步 `requirements.txt`（B9）并 `uv lock --frozen` 校验。
