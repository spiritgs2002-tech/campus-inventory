# P7 运维说明

日期：2026-10-31。完整契约、配置与启动命令见 ../README.md 的“P7 受控清理与调度”。

## 上线前配置

1. 使用专用数据库普通运行 LOGIN；先执行 `manage.py verify_runtime`，不得用 owner/超级用户运行 worker 或人工清理。
2. 将学校租户 ID 与已改密、启用的管理员 ID 写入 `MAINTENANCE_ACTORS_JSON`。不要使用示例 ID；停用、降权或强制重置该审计身份后，维护会拒绝执行，先更新有效身份配置再重启进程。
3. 学校确认 `ATTACHMENT_RETENTION_DAYS`、证据历史版本和保全策略。默认 `ATTACHMENT_CLEANUP_ENABLED=false`；无需为了启动会话清理开启证据删除。
4. 核验 S3 私有策略、条件删除能力、桶从未启用版本控制，测试账号能查版本状态及限定前缀 LIST/HEAD/DELETE。云存储服务若不支持这些契约，应保持证据清理关闭并完成适配验收。
5. 确认 Redis 不对公网开放、队列环境隔离；准备 beat 持久计划目录，每套部署只启一个 beat。
6. 先执行本校 dry-run，核对对象保留边界后分批执行。默认25；若积压超过批量上限，可人工使用新键逐批推进，不能提高批量后复用同一键。

## 常规运行与失败处理

- sessions：整族最后 token 过期超过30天才删；保留重用检测证据。异常跨族 parent 引用会跳过并在 `skipped_cross_family` 返回族 ID，应人工排查来源，禁止强删活跃后继。
- responses：按完成时间90天，仅清 response。业务引用、摘要和旧键继续有效，不允许 DELETE operation_requests。业务端处理 ALREADY_PROCESSED 时使用 business_refs 查询授权范围内结果。
- evidence：deleted_at 墓碑先提交，随后物理删除。网络超时、503 或数据库失败可能导致“已隐藏/未完成物理清理”，原键重试；不得清墓碑、删元数据或关联来掩盖失败。`maintenance.evidence.deleted` 完成记录长期保留，即使其 response 已清，也不会重新选作待清理对象。
- orphans：至少24小时未登记才候选，删除前再次检查登记及对象版本。每次只扫描一页，游标继续后续页；全轮结束重新开始。失败页原键重试；即使未手工重试，后续扫描轮次仍会重新遇到未删除对象。
- 高延迟、连续失败或大量积压：停止 beat；必要时先将两项开关改 false 并重启 worker，避免继续消费删除任务；保留计划、审计及对象状态，排查后原键重试。不要仅依赖 Celery SUCCESS，业务 `ok=false` 与 ERROR 均需运维监控。
- 锁冲突返回 RETRYABLE_LOCK_CONFLICT 时保留原键重试；非重试错误（无效身份、配置缺失、版本桶拒绝）先修配置。批次耗时过长应降低 batch-size 并使用新键，禁止修改已冻结参数。
- 外部直接写库、替换对象、修改桶版本策略不参与应用租户锁，必须暂停清理后由受控变更流程执行。
